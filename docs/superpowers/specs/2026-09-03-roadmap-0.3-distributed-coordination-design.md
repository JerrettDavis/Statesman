# ROADMAP 0.3: durable distributed coordination — design

Status: approved for spec review
Date: 2026-09-03
Scope: all eight items listed under `ROADMAP.md` § "0.3: durable distributed coordination"

## Problem

Statesman's core ledger contract (`IStateLedgerStore`, `src/Statesman.Abstractions/Ledger.cs:221`) is
deliberately process-local: `AppendAsync` gives per-address optimistic concurrency
(`StateWriteCondition`, `Ledger.cs:171`) and nothing more. Every distributed guarantee the docs
gesture at — cross-process coherent capture, leader election for maintenance workers, durable
resumable change feeds, partition enumeration, replication-lag visibility, portable
import/export, and outbox delivery — is either absent or implicitly scoped to a single process,
and the docs say so explicitly (see the exhaustive gap inventory this design is based on, captured
in this session's background research). `ROADMAP.md` groups these eight gaps as milestone 0.3 with
one exit criterion:

> no distributed method silently falls back to process-local semantics; capability discovery
> tells callers exactly which guarantee is available.

This document designs how all eight items get built coherently, on one shared mechanism, rather
than as eight unrelated features.

## Grounding: what exists today

- `IStateLedgerReplica` (`Ledger.cs:248`) is a one-member optional interface (`ImportAsync`) that a
  store implements only if it can accept exact records. Consumers discover it via `as`/`is`. This
  is the **only** capability-negotiation precedent in the codebase — there is no descriptor,
  registry, or `Supports(...)` method anywhere else in `src/`.
- `StateRecord` carries `Revision` (per-address) and `GlobalPosition` (store-wide,
  `Ledger.cs:16`) as separate fields. Redis assigns `GlobalPosition` via `INCR` *before* the
  conditional write commits (`RedisStateLedgerStore.cs:119`), so position is consumed even on a
  failed CAS — `GlobalPosition` is monotonic but **sparse**, never a count.
- `StatesmanRuntime.CaptureAsync` (`StatesmanRuntime.cs:160`) takes an in-process `CommitGate`
  semaphore before computing a snapshot's position — the "coherent capture" guarantee is scoped to
  that gate's process lifetime, nothing more.
- `StatesmanHostedService.ExecuteAsync` (`StatesmanHostingExtensions.cs:72`) runs a `PeriodicTimer`
  and calls `root.MaintainAsync` on every tick, in every process, with no coordination.
- `StateChangeHub<T>` (`StateChangeHub.cs`) is a live, in-memory, bounded/drop-oldest fanout
  (`Channel.CreateBounded(..., FullMode = DropOldest)`) — by design not durable (ADR 0004:
  "observation is not delivery").
- No shared provider conformance suite exists yet (ROADMAP 0.2 item, still aspirational). Each
  provider has its own test project under `tests/`.
- Provider-side primitives found: FileSystem uses per-address `SemaphoreSlim`s (in-process only,
  no cross-machine lock); Redis has the `GlobalPosition` counter but no lock/lease primitive
  in-code; Tiered has read-mode policy knobs (`PreferHot`, `ServeHotWhenColdUnavailable`) but no
  lag metadata field on any type; EF Core has no distributed primitive found.

## Architecture: one capability-negotiation convention for all eight items

Added to `Statesman.Abstractions` (Phase 0, shipped):

```csharp
public interface IStateCapability { }

public static class StateCapabilityExtensions
{
    public static bool TryGetCapability<TCapability>(
        this IStateLedgerStore store,
        [NotNullWhen(true)] out TCapability? capability)
        where TCapability : class, IStateCapability
    {
        capability = store as TCapability;
        return capability is not null;
    }
}
```

`IStateLedgerReplica` is retrofitted to extend `IStateCapability` so the existing precedent and all
new capabilities share one idiom. No registry, no descriptor object — a provider either implements
the interface or it doesn't, so the capability surface can never drift from what is actually
implemented (enforced by a reflection-based completeness test, see Testing). Every new distributed
capability below is `I<Name> : IStateCapability`, discovered exclusively through
`TryGetCapability`. `[NotNullWhen(true)]` is required on the `out` parameter — without it, the
documented `if (store.TryGetCapability(out X? x)) { x.Method() }` pattern fails to compile cleanly
under this repo's `TreatWarningsAsErrors=true` (CS8602).

`docs/architecture/capabilities.md` (new) becomes the single table of capability interface ×
provider, kept honest by a conformance test (see Testing) that asserts the doc matches
`TryGetCapability` results at runtime.

### Capability forwarding through wrapping stores

`TryGetCapability` is a plain `as` cast on the concrete store. `TieredStateLedgerStore` wraps a hot
and a cold `IStateLedgerStore` without implementing any capability itself, so a Tiered store over a
Redis hot tier would report `TryGetCapability<IStateLeaseProvider>() == false` in Phase 1 even
though a lease provider exists one level down — same problem for Phase 2's `IStateChangeNotifier`.
(Phase 5's `IReplicationLagSource` is unaffected: Tiered implements that one itself, since lag is a
property of the tiering relationship, not something to forward.)

Resolution: an opt-in escape hatch, consulted only after the direct cast fails, so it changes
nothing for any store that doesn't implement it:

```csharp
public interface IStateCapabilityProvider
{
    bool TryGetCapability(Type capabilityType, out object? capability);
}
```

`TryGetCapability<TCapability>` tries the direct cast first; on failure, if the store implements
`IStateCapabilityProvider`, it consults that and casts the result. `TieredStateLedgerStore` adopts
`IStateCapabilityProvider` in whichever phase first ships a capability it needs to forward (Phase 1
for leases) — delegating to whichever of its hot/cold stores can back the request, per that phase's
own policy for which tier is authoritative. This is source- and binary-compatible to add once and
does not need revisiting per phase.

### Signaling convention

Every capability-gated call site follows one of two documented behaviors — decided per capability
below, never improvised per call site:

- **(a) Documented degradation**: `TryGetCapability` returns false → the caller runs its existing
  process-local behavior and logs a defined event noting distributed coordination is unavailable.
  Used only where the degraded behavior is safe and was already the pre-0.3 behavior (e.g.
  maintenance workers without a lease provider).
- **(b) Hard failure**: `TryGetCapability` returns false → the caller throws
  `NotSupportedException` naming the missing capability. Used wherever silently returning a
  weaker guarantee than requested would be incorrect (e.g. distributed capture must never
  quietly return a process-local snapshot).

## Phases

Phases are dependency-ordered; each is one PR-sized (or small PR series) unit landing on `main`
with green CI before the next begins.

### Phase 0 — Foundation (shipped)

`IStateCapability`, `TryGetCapability<T>`, retrofit `IStateLedgerReplica`, add
`docs/architecture/capabilities.md` backed by a reflection-based completeness test. No provider
behavior change. Unblocks every later phase. Landed on `main` 2026-09-03. `IStateCapabilityProvider`
(capability forwarding, above) was designed during this phase's final review; it shipped in Phase 1,
its first consumer (`TieredStateLedgerStore` forwarding `IStateLeaseProvider`).

### Phase 1 — Leases (`IStateLeaseProvider`) (shipped)

```csharp
public interface IStateLeaseProvider : IStateCapability
{
    ValueTask<IStateLease?> AcquireAsync(string leaseId, TimeSpan ttl, CancellationToken ct);
}

public interface IStateLease : IAsyncDisposable
{
    ValueTask<bool> RenewAsync(TimeSpan ttl, CancellationToken ct);
}
```

- **Redis**: `SET NX PX` to acquire, Lua compare-and-delete to release. Single-instance
  consistency only — documented as such, not Redlock/quorum.
- **EF Core**: a lease row with an expiry column, acquired via an optimistic conditional update.
  Expiry is evaluated against the acquiring process's own clock, not enforced server-side (unlike
  Redis's TTL) — clock skew between replicas is a real, if small at a 30s TTL, property of this
  provider's mutual exclusion.
- **FileSystem, in-memory**: do not implement it (consistent with the existing "don't point
  multiple writers at a shared network directory" caveat, `docs/providers/index.md:21`).
- Leasing lives in `StatesmanRuntime.MaintainAsync`, not `StatesmanHostedService`: `IStatesman`
  (the public interface `StatesmanHostedService` holds) exposes no store reference, and a single
  root is not backed by one store — each `StateHandle<T>` resolves its own store independently via
  `Manifest.Store`, a plain string, so different state keys under the same root can live in
  different stores. `MaintainAsync` groups its due handles by `Manifest.Store`, resolves each named
  store, and acquires a lease per group (`$"{Id}:{storeName}:maintenance"`, where `Id` is the
  declaration's stable root name, not a per-process id) before refreshing that group when the store
  supports leases; falls back to today's per-process behavior, tracked internally (mirroring the
  existing `MaintenanceFailures` pattern, not a new logging dependency) when it doesn't. This is
  signaling case (a). `StatesmanHostedService` itself is unchanged. (This corrects the mechanism
  placement originally specced above; caught during Phase 1's Task 2 review, 2026-09-03.)
- `TieredStateLedgerStore` implements `IStateCapabilityProvider` (shipped in Phase 1, not deferred
  to when Phase 1 needed it as originally noted above — it was Phase 1 that needed it), forwarding
  to whichever of its hot/cold stores implements `IStateLeaseProvider` (hot first, since hot is
  where maintenance contention actually happens). **Open design question, still live:** this
  hot-first forwarding is currently unconditional for *every* capability type, not just leases —
  correct for leases, but would be wrong for an authoritative-store-shaped capability discovered
  *through* this forwarding path (cold, typically, should win for those). Resolved for
  `IStateChangeFeed` specifically in Phase 2 below — it turned out not to need Tiered's forwarding
  at all, since every provider implements it directly and Tiered delegates straight to cold like
  `ReadHistoryAsync` already does. The general policy question remains open for whatever capability
  next relies on `IStateCapabilityProvider` forwarding through Tiered (e.g. Phase 4's distributed
  capture) — resolve it then, don't inherit hot-first by accident.
- **Not implemented in Phase 1, tracked for a hardening pass:** `IStateLease.RenewAsync` exists and
  is implemented/tested by both providers but has no production caller — the fixed 30s
  `MaintenanceLeaseTtl` is a hard cap with no renewal, so a refresh that runs longer than 30s loses
  its exclusion guarantee mid-flight. A shared conformance suite per capability interface (see
  Testing, below) was also deferred to when a third provider exists; in the meantime both Redis and
  EF Core cover acquire/deny/expire/renew but not the specific property that a stale (already
  superseded) lease holder's `DisposeAsync` must not release/renew a *successor's* lease — this is
  the safety property the whole feature rests on and should not go untested indefinitely.

### Phase 2 — Durable change feed (shipped) + provider-native notifications

```csharp
public interface IStateChangeFeed : IStateCapability
{
    IAsyncEnumerable<StateChangeEnvelope> ReadAsync(StateChangeCursor? from, CancellationToken ct);
}
```

**Revised after Phase 2 research, 2026-09-03 (see Addendum below for why):** this is NOT built as a
generic decorator over `ReadHistoryAsync`. `ReadHistoryAsync` is scoped to one already-known
`StateAddress` (`Ledger.cs:238-241`); a change feed needs to discover records across *every*
address in a store since a cursor — a fundamentally different query shape only EF Core's existing
schema supports natively (its `StatesmanRecords` table has a real, unique-indexed `GlobalPosition`
column spanning every stream). Redis, FileSystem, and in-memory have no such cross-stream index
today.

Each provider implements `IStateChangeFeed` **directly and natively**, doing real cross-stream
work:
- **EntityFrameworkCore**: `SELECT * FROM StatesmanRecords WHERE GlobalPosition > @cursor ORDER BY
  GlobalPosition` against the existing indexed column — no schema change needed.
- **Redis**: a new global sorted set (`{prefix}:{name}:changes`, scored by `GlobalPosition`,
  storing the serialized record directly, mirroring the existing per-stream history sorted set's
  storage shape) populated by an additional write inside `AppendAsync`'s existing transaction.
  `ReadAsync` is `SortedSetRangeByScoreAsync` with an exclusive lower bound at the cursor.
- **FileSystem**: a single append-only global index file, written under its own lock alongside
  each `AppendAsync`, storing `{position}\t{address.Canonical}\t{revision}` per line; `ReadAsync`
  scans forward from the cursor and re-reads each referenced record from the existing per-address
  storage. Not optimized (an O(appends-since-cursor) scan) — acceptable for now, and a natural
  candidate for ROADMAP 0.2's still-unbuilt "filesystem recovery and compaction tooling" to
  optimize later with a real index, not a scope concern for Phase 2.
- **In-memory**: a `List<StateRecord>` (or equivalent) appended to under the existing per-stream
  gate's sibling lock, alongside `_streams`; already naturally position-ordered.
- **Tiered**: delegates directly to `_cold`'s `IStateChangeFeed` — the ledger's authoritative
  source, matching `TieredStateLedgerStore.ReadHistoryAsync`'s existing (and correct) behavior of
  always reading history from cold regardless of `ReadMode` (`TieredStateLedgerStore.cs:88-95`).

This resolves the capability-forwarding risk the Phase 1 addendum flagged for this exact
capability: there is no resolution-time decorator, so there is nothing that needs to *also*
implement `IStateCapabilityProvider` to keep other forwarded capabilities (like leases) working
through it. `IStateChangeFeed` is discovered exactly like any other Phase 0-style capability —
`TryGetCapability<IStateChangeFeed>` — and, because every provider implements it directly under
this design, it is universal in effect without being architecturally special-cased. A provider that
can't back it (none currently) would report unsupported honestly (signaling case (b)) rather than
silently degrading through a generic adapter.

`StateChangeCursor` opaquely wraps a store's `GlobalPosition`; it is never treated as a count or
used arithmetically by callers, only round-tripped. `StateChangeEnvelope` carries the `StateRecord`
plus the `StateChangeCursor` to resume from after it.

`IStateChangeNotifier : IStateCapability` (Redis pub/sub) is a genuinely optional low-latency push
hint that `StateChangeHub` may subscribe to, but any consumer needing correctness must still
reconcile through `IStateChangeFeed` — push accelerates, feed is authoritative. This preserves ADR
0004's boundary: notification is still not delivery; the feed is what makes delivery durable.

### Phase 3 — Partition discovery (`IPartitionCatalog`)

```csharp
public interface IPartitionCatalog : IStateCapability
{
    IAsyncEnumerable<StatePartitionDescriptor> ListPartitionsAsync(CancellationToken ct);
}
```

Implementable by all five current providers (InMemory, FileSystem, Redis, EF Core, Tiered) — the
roadmap's "for stores that can support it efficiently" hedge does not exclude any shipped provider
today.

**Corrected during Phase 3 planning, 2026-09-04:** the specific per-provider mechanisms first
sketched above (FileSystem directory enumeration, Redis `SCAN` by key pattern, EF Core
`SELECT DISTINCT`) turned out not to work as stated — a pure technical correction, not a
completeness/cost trade-off, so resolved directly rather than put to the user (matching the Phase 1
lease-mechanism-placement precedent). Both FileSystem's per-address directories and Redis's
per-stream keys are SHA-256 hashed (`FileSystemStateLedgerStore.StreamDirectory`,
`RedisStateLedgerStore.StreamKey`), so neither a directory walk nor a key-pattern `SCAN` can recover
the original `StateAddress` at all — not merely inefficient, genuinely impossible. The actual plan:
FileSystem reuses Phase 2's existing plaintext `_changes.log` (which already carries full address
components per line); Redis adds a small new Hash (`{prefix}:{name}:partitions`) written inside the
same `AppendAsync` transaction that already writes the Phase 2 change-feed sorted set — the same
"add a native per-provider index" pattern Phase 2 already established, not a new architectural
choice. EF Core doesn't need `SELECT DISTINCT` at all: its existing `StatesmanHeads` table already
holds exactly one row per partition (it's the head/latest-revision table), so `ListPartitionsAsync`
is a plain `AsNoTracking()` enumeration of it, cheaper than scanning `StatesmanRecords`. See
`docs/superpowers/plans/2026-09-04-roadmap-0.3-phase-3-partition-catalog.md` for the exact code.

### Phase 4 — Distributed coherent capture (`IDistributedCapture`)

```csharp
public enum StateCaptureConsistency { ProcessLocal, ReadCommittedDistributed, SnapshotDistributed }

public interface IDistributedCapture : IStateCapability
{
    ValueTask<StateSnapshotSet> CaptureAsync(
        IEnumerable<StateReference> references, StateCaptureConsistency required,
        StateReadOptions? options, CancellationToken ct);
}
```

Only providers that can back a real cross-process guarantee implement it — EF Core via a
serializable transaction, Redis via `MULTI`/`EXEC` best-effort. FileSystem does not implement it.
Requesting a consistency level a provider can't back, or calling on a provider without the
capability at all, is signaling case (b): `NotSupportedException`, never a silent process-local
capture returned as if it were distributed.

**Corrected during Phase 4 planning, 2026-09-04:** the interface as first sketched above takes
`StateReference`, but `StateReference` (`Identity.cs:139`) has no `Root` — it identifies a declared
state within one already-known `IStatesman` root, not a store-level address, and a single store can
back multiple roots. The store-level capability actually takes `StateAddress`
(`Identity.cs:118`, the type every other store-facing method already uses):

```csharp
public interface IDistributedCapture : IStateCapability
{
    ValueTask<IReadOnlyDictionary<StateAddress, StateRecord?>> CaptureAsync(
        IEnumerable<StateAddress> addresses, StateCaptureConsistency required, CancellationToken ct);
}
```

**A second, related correction:** the store-level method also drops `StateReadOptions` and does not
return `StateSnapshotSet` — both are runtime-shaped concerns the store has no way to honor.
`StateReadOptions` (`Cached`/`Current`/`Fresh`) governs per-handle cache freshness, a concept that
only exists at the runtime/handle layer (`IStateHandleInternal.GetUntypedAsync`); a store-level
capture is inherently a fresh, current read of the ledger, like `ReadLatestAsync` (which itself
takes no `StateReadOptions` either). And building an `IStateSnapshot` requires deserializing
`StateRecord.Payload` against a specific CLR type, migration table, and `IStateSerializer` — all
runtime/declaration concerns (`RuntimeDefinition.cs:70-122`) a store has neither access to nor any
business performing. The store-level capability therefore returns raw, per-address
`StateRecord?` (mirroring `IStateLedgerStore.ReadLatestAsync(StateAddress, ct) : StateRecord?`,
generalized to many addresses read coherently in one call; `null` per address means "no record yet",
same as `ReadLatestAsync`), and the *runtime* converts each into a typed `IStateSnapshot` via the
already-existing internal `IStateRuntimeDefinition.CreateSnapshot(address, record, serializer,
observedAt)` (`RuntimeDefinition.cs:16-20,63-68`) — the same method `StateHandle<T>` already uses
internally, just invoked directly instead of through a handle's cached state.

`StateSnapshotSet` and the runtime-level, `StateReference`-based `IStatesman.CaptureAsync` /
`IStateContainer.CaptureAsync` already exist and ship today (`RuntimeContracts.cs:126,183`,
implemented in `StatesmanRuntime.CaptureAsync`, `StatesmanRuntime.cs:164-196`) — that existing
implementation (hydrate each handle, take the in-process `CommitGate`, snapshot
`CurrentUntyped`) *is* today's `StateCaptureConsistency.ProcessLocal`, just not yet named as a level.
Phase 4 adds a `StateCaptureConsistency required = ProcessLocal` parameter to the runtime-level
methods, inserted right after `references` so `CancellationToken` stays the last parameter (default
preserves today's behavior; the one existing 3-positional-argument call site,
`StateFixture.cs:115`, moves to named arguments rather than relying on position) rather than
inventing a second capture path: when a distributed level is requested, `StatesmanRuntime.CaptureAsync`
groups the requested handles by resolved store (same `GroupBy(handle => handle.Manifest.Store)` shape
`MaintainAsync` already uses for lease grouping, `StatesmanRuntime.cs:312`), resolves each group's
store, calls `TryGetCapability<IDistributedCapture>()` per store, calls its `CaptureAsync` with just
that group's addresses, merges the returned per-address `StateRecord?`s across groups, and builds the
final `StateSnapshotSet` by running each requested handle's address and its resolved record through
`IStateRuntimeDefinition.CreateSnapshot` — throwing `NotSupportedException` (case (b)) if any group's
store lacks the capability, never falling back to `ProcessLocal` silently. (`StateCaptureConsistency`
itself is not re-validated by the runtime beyond routing — each store's own `CaptureAsync`
implementation is responsible for rejecting a level it personally cannot back.)

Per-provider mechanism, corrected against the actual client APIs:
- **EF Core**: reuses the transaction pattern `AppendAsync`/lease `AcquireAsync` already use
  (`context.Database.BeginTransactionAsync(IsolationLevel, ct)`,
  `EntityFrameworkStateLedgerStore.cs:133-135,221-223`) — open one transaction, read every requested
  address's `StatesmanHeads` row inside it, commit. `ReadCommittedDistributed` and
  `SnapshotDistributed` map to real, different isolation levels (`ReadCommitted` vs. `Serializable`)
  on the same one transaction-per-call shape — an honest, not cosmetic, distinction.
- **Redis**: the spec's original "`MULTI`/`WATCH`" phrasing is corrected — `WATCH` is a
  write-conflict-detection primitive and has no role in a pure read. The actual mechanism is an
  unconditional `MULTI`/`EXEC` batch of `StringGetAsync(HeadKey(address))` per requested address
  (same `ITransaction` API `AppendAsync` already uses for its conditional writes,
  `RedisStateLedgerStore.cs:141-162`, just without `AddCondition` since nothing is being compared).
  On standalone Redis, command execution is single-threaded, so a `MULTI`/`EXEC` batch is a true,
  exact atomic snapshot, not merely "best-effort" — `ReadCommittedDistributed` and
  `SnapshotDistributed` are not distinguishable on this provider and should be accepted and honored
  identically by the same one code path, rather than built as two. The real best-effort boundary is
  **Redis Cluster**: addresses whose keys land in different hash slots can't share one `MULTI`/`EXEC`
  (`CROSSSLOT`), so a cluster-mode capture spanning slots must throw `NotSupportedException` rather
  than silently degrading to unsynchronized sequential `GET`s.
- **FileSystem**: confirmed to have no cross-process, multi-file transactional primitive at all
  (its gates are in-process `SemaphoreSlim`s only) — "does not implement it" stands as specced, same
  rationale as Phase 1's lease non-implementation.
- **Tiered**: implements `IDistributedCapture` directly and delegates straight to `_cold`, throwing
  `NotSupportedException` if cold lacks it — the same pattern `IStateChangeFeed` and
  `IPartitionCatalog` already established (`TieredStateLedgerStore.cs:104-121`), not generic
  `IStateCapabilityProvider` forwarding. This is correct, not just consistent: capture's entire
  purpose is a coherent guarantee over the *authoritative* store, and hot is explicitly
  non-authoritative everywhere else in this codebase. It also means this is the third consecutive
  capability (after the change feed and partition catalog) to sidestep the open
  hot-first-forwarding-policy question from the Phase 1 addendum by being implemented directly on
  Tiered — that general policy question can stay deferred; no shipped capability actually depends on
  it today.

**Also resolved in this phase, not parked a second time:** the Phase 1 addendum's parked EF Core
lease race. `AcquireAsync` (`EntityFrameworkStateLedgerStore.cs:211-251`) opens its transaction,
checks for an existing unexpired lease, then `Add`s or updates a row and calls
`SaveChangesAsync`/`CommitAsync` **with no `catch` at all** — unlike `AppendAsync`, which wraps the
same shape in `catch (DbUpdateException)` and reconciles (`EntityFrameworkStateLedgerStore.cs:196-208`).
Two concurrent first-acquisitions both observe no existing row, both `Add` a row with the same
`LeaseId` primary key, and the loser's `SaveChangesAsync`/`CommitAsync` throws an uncaught
`DbUpdateException` (PK violation) instead of `AcquireAsync` returning `null` — the interface's own
documented "someone else got it" outcome (`Ledger.cs:270-274`). Phase 4 fixes this by mirroring
`AppendAsync`'s existing catch/rollback/re-read pattern exactly, since Phase 4's own EF Core work
depends on the same transaction-retry-on-conflict shape for capture.

### Phase 5 — Replication lag metadata (`IReplicationLagSource`)

```csharp
public interface IReplicationLagSource : IStateCapability
{
    ValueTask<StateReplicationLag> EstimateLagAsync(CancellationToken ct);
}
```

Implemented by `Statesman.Persistence.Tiered`, comparing hot vs. cold `GlobalPosition`. Feeds the
0.2 OpenTelemetry semantic-conventions work as an additional metric source.

**Refined during Phase 5 planning (2026-09-04), verified against current code:** the sketch above is
feasible as written, but "comparing hot vs. cold `GlobalPosition`" needs a concrete source for each
tier's newest position, and `IStateLedgerStore` has no such member. Phase 3's `IPartitionCatalog`
is that source: every provider yields one `StatePartitionDescriptor` per partition whose
`LastPosition` is that partition's head `GlobalPosition`, and `IStateLedgerReplica.ImportAsync`
preserves `GlobalPosition` exactly on every replica (InMemory, FileSystem, and EF Core each advance
their own counter to the imported position rather than re-allocating), so a hot head at the same
position as its cold head is genuinely the same record. Tiered therefore estimates lag by
enumerating **hot's catalog first, then cold's** (so an authoritative write landing mid-estimate can
only over-report lag, never under-report it), and reports:

```csharp
public sealed record StateReplicationLag
{
    public required long AuthoritativePosition { get; init; } // cold's newest head position, 0 when empty
    public required long ReplicaPosition { get; init; }       // hot's newest head position, 0 when empty
    public required int PartitionsBehind { get; init; }       // cold partitions hot lacks or holds at an older position
    public long PositionGap => Math.Max(0, AuthoritativePosition - ReplicaPosition);
    public bool IsCaughtUp => PartitionsBehind == 0 && PositionGap == 0;
}
```

Consequences worth stating plainly: (1) both tiers must implement `IPartitionCatalog` or
`EstimateLagAsync` throws `NotSupportedException` (case (b)) — true of all five shipped providers;
(2) `PositionGap` is a distance in a **sparse** sequence (Redis consumes a position on a failed
CAS), never a record count; (3) the hot tier is populated lazily by reads and writes routed through
the tiered store, so `PartitionsBehind` counts partitions the replica has simply never been asked
for as well as ones it holds stale — this is honest for a replica-lag metric and is documented,
not hidden; (4) the estimate's cost is one catalog enumeration per tier, which on FileSystem is
O(total writes) (Phase 3's documented cost) — acceptable for a polled metric, not for a hot path;
(5) `EstimateLagAsync`'s token gets the `= default` every other capability method in `Ledger.cs`
has, a cosmetic deviation from the sketch. No metric instrument is registered in this phase:
`StatesmanTelemetry`'s `Meter` is synchronous-callback (`ObservableGauge`) territory and catalog
enumeration is async, so the capability ships as the pollable source the 0.2 telemetry work can
sample from a hosted loop later, rather than a half-wired gauge now.

### Phase 6 — Import/export/restore tooling

New library (`Statesman.Tooling`, name TBD at plan time) built on the existing
`IStateLedgerReplica.ImportAsync`. Export format carries the declaration fingerprint and a schema
version; restore validates both against the target's current fingerprint before importing, and
refuses (case (b)) on mismatch rather than importing incompatible history.

#### Refined during Phase 6 planning (2026-09-04)

Planning research verified the sketch above against the code and refined it in four places. The
user was consulted (`AskUserQuestion`) on the first three; the fourth is a planning ruling.

- **Redis gains `IStateLedgerReplica`.** The sketch builds restore on `ImportAsync`, but Redis was
  the one non-tiered provider without it (`docs/architecture/capabilities.md`). Nothing structural
  prevents it: `RedisStateLedgerStore.AppendAsync` already writes head, revision guard, history
  sorted set, change-feed sorted set, and partition hash inside one `MULTI`/`EXEC`, so an exact import
  is the same transaction shape keyed by the record's own `Revision`/`GlobalPosition`, plus a
  max-advance of the `global-position` counter (a small Lua script, run *before* the transaction so
  no concurrent append can ever allocate a position at or below the imported one). The alternative —
  restore refusing Redis with `NotSupportedException` — would have left a "No" cell that reflects
  missing work rather than a genuine limitation, which the capability convention is meant to avoid.
  Restore therefore works on every shipped provider except Tiered (restore into its cold store
  directly; Tiered deliberately does not implement `IStateLedgerReplica` because cold is
  authoritative). Redis also becomes eligible as a Tiered hot tier.
- **Export reads `IPartitionCatalog` + per-partition `ReadHistoryAsync`, not `IStateChangeFeed`.**
  The feed is documented at-least-once with possible tail loss under concurrent writes (post-Phase-2
  addendum) and its prune interaction is provider-inconsistent (Redis/InMemory retain pruned records
  forever, EF Core loses them). Enumerating the catalog (every shipped provider has one), filtering to
  the manifest's root, sorting partitions by `Canonical`, and streaming each partition's full history
  oldest-first gives an export that is complete for every *retained* revision, deterministic in
  layout, streamable without materializing, and free of both feed caveats. What it is **not** is a
  cross-partition point-in-time snapshot: a write concurrent with the export may or may not appear,
  per partition. The documented promise is therefore "every revision the source retains for every
  partition its catalog lists under this root, each partition read atomically-enough for its own
  provider; quiesce writers for a consistent backup." Implementation trap found: `StateHistoryOptions`
  defaults `Take` to 100 and `NewestFirst` to true — export must pass `Take = null, NewestFirst = false`
  explicitly or silently truncate long histories.
- **Package name is `Statesman.Tooling`** (the sketch's suggestion), namespace `Statesman.Tooling`,
  depending only on `Statesman.Abstractions`. Public surface: `StateLedgerExport.ExportAsync` /
  `ExportToFileAsync`, `StateLedgerRestore.RestoreAsync` / `RestoreFromFileAsync`, their options and
  summary records, the format DTOs (`StateLedgerExportHeader` / `StateLedgerExportRecord` /
  `StateLedgerExportTrailer`), and `StateLedgerRestoreException`.
- **Where the fingerprint lives, and what "schema version" means.** The declaration fingerprint is
  `StatesmanManifest.Fingerprint` (SHA-256 of the canonical compact manifest JSON, computed once by
  `StatesmanDeclarationBuilder.Build`). **No store persists it** — nothing under
  `src/Statesman.Persistence.*` knows the fingerprint — so export and restore both take the
  `StatesmanManifest` as an explicit argument (the runtime exposes it as `IStatesman.Manifest`), and
  restore compares the export header's fingerprint against the manifest the operator supplies, not
  against anything the target store recorded. The "schema version" the sketch mentions is the
  **export format version** (`statesman.ledger-export/v1`, mirroring `StateFixture`'s
  `statesman.fixture/v1`), refused when unrecognized; per-record `SchemaVersion` is carried verbatim
  and *not* validated, because exact restore reproduces history as it was and the runtime's declared
  migrations upgrade old schema versions at read time exactly as they would for the original store.

**Refusal is total, never partial (case (b) as the sketch requires, plus two validation refusals):**
restore reads and validates the entire export — format, root, fingerprint, every record's
`StateRecord.Validate()`, and the trailer's record count (a truncated file has no trailer or a count
mismatch) — before contacting the target at all; then checks `IStateLedgerReplica`
(`NotSupportedException` if missing); then, by default, refuses a target whose `IPartitionCatalog`
already lists any partition under the export's root, because `GlobalPosition` values from
independent histories collide (EF Core's unique index on `GlobalPosition` would fail *mid-import*,
the exact partial-import outcome the sketch forbids; other providers would silently interleave).
`AllowNonEmptyTarget` opts out for the two legitimate cases: re-running a restore after a
store-side failure mid-import (every `ImportAsync` is exact and idempotent, so re-running is the
recovery path) and restoring over a store known to share the export's position lineage. Format is
newline-delimited JSON — one header line, one line per record, one trailer line — so both directions
stream and the header is checkable before a single record is parsed.

**Found and fixed during Phase 6 execution (2026-09-04, commit `cafdfbe`):** the planning refinement
above said Tiered "deliberately does not implement `IStateLedgerReplica`", and that was true of the
class's interface list — but `TryGetCapability<IStateLedgerReplica>` on a Tiered store still
*succeeded*, because `TieredStateLedgerStore.TryGetCapability(Type, out object?)` forwards every
capability hot-first and the Tiered constructor requires the hot store to implement
`IStateLedgerReplica`. Task 4's cross-provider test (restore into a Tiered store must throw
`NotSupportedException` pointing at cold) caught it: restore silently imported every record into the
hot cache and the cold authority never saw them. The fix is a veto inside the generic forwarder —
`IStateLedgerReplica` is never forwarded through a Tiered store, with a regression test in
`TieredCapabilityForwardingTests` and a clause in `docs/architecture/capabilities.md`. The rejected
alternative was forwarding it to *cold* (so restore-into-Tiered would mean restore-into-cold): under
`PreferHot` a stale hot head would then be served after the restore, so forcing operators to target
the cold store is the safer contract. This is the first concrete data point on the long-deferred
Tiered forwarding-policy question: generic hot-first forwarding is wrong for any capability whose
semantics are "authoritative write", and the plan's pre-flight scan should have checked the
forwarder, not just the interface list, when it assumed a capability was absent.

**Found by the Phase 6 final whole-branch review and fixed in the fix wave (2026-09-04):** the Redis
bullet above claimed the Lua max-advance made position reuse impossible. It did not, and worse, the
change feed could silently lose records: Redis sorted-set scores are IEEE doubles (exact only for
integers up to 2^53), the Redis change feed scores its members by `GlobalPosition`, and the
filesystem provider allocates positions from UTC ticks (about 6.4e17). So a filesystem export
restored into Redis — a documented, default-options path — had adjacent positions rounding to the
same score, the exact-replace import's remove-by-score deleting the neighbouring record, and the
Lua `tonumber` comparison failing to advance the counter. The reviewer reproduced both against a
live Redis; the planning-time verification checked that the script ran inside/outside `MULTI` but
never asked whether its *arithmetic* was exact. The fix: `RedisStateLedgerStore.ImportAsync` refuses
any position above `MaxImportablePosition` (2^52 — half the exact range, so the appends that follow
a restore stay exact for another 2^52 positions) with `NotSupportedException` before touching any
key, the Lua script compares canonical decimal strings instead of doubles, and the docs state the
bound: a filesystem export cannot be restored into Redis (restore it into in-memory, filesystem, or
EF Core). Reshaping the feed to an exact large-position representation (a lexicographic sorted set
keyed by zero-padded position, say) would lift the bound and is a candidate follow-on, not Phase 6
scope. The same review also tightened restore (a record line whose `root` differs from the header's
root is now refused — the fingerprint check alone did not cover hand-merged files), made
`ExportToFileAsync` write to a sibling temporary file and move it into place only on success (a
failed export previously destroyed the previous backup at that path), and corrected the guide's
description of the non-empty-target hazard (in-memory/filesystem interleave, EF Core fails on its
unique index, Redis *overwrites* the colliding entry). Generalization worth carrying into Phase 7's
planning: when a plan adopts a provider primitive (a Lua script, a sorted-set score, a column type),
the pre-flight scan must state that primitive's value domain and confirm the data fits it — two of
this phase's three real defects (this one and the Tiered forwarder) came from checking the wrong
layer.

### Phase 7 — Outbox bridges

Adapter package(s) (e.g. `Statesman.Outbox.*`) consuming `IStateChangeFeed` with a persisted
cursor, delivering at-least-once to a message broker. Strictly a consumer of the durable feed from
Phase 2 — introduces no new core concept and keeps observation (`StateChangeHub`) distinct from
delivery, per ADR 0004. Must land after Phase 2.

## Testing

ROADMAP 0.2's shared provider conformance suite doesn't exist yet; this plan builds the minimal
version needed for 0.3:

- One conformance test base class per capability interface (e.g. `LeaseProviderConformanceTests`),
  inherited by every provider test project that implements that capability.
- A capability-matrix test asserting `docs/architecture/capabilities.md` matches actual
  `TryGetCapability` results across all shipped providers, so the doc can never silently drift from
  the code. This must include a completeness check (reflection over all `IStateCapability`
  implementers and all `IStateLedgerStore` implementations in the referenced assemblies) — a
  per-cell check alone passes silently when a new capability or provider ships without a matching
  row/column, which is the actual drift risk each later phase introduces.
- Each phase's PR(s) must leave `main` green (full CI: build, test, pack, analyzers, docs) before
  the next phase begins.

## Non-goals (unchanged)

This design does not turn Statesman into a distributed transaction coordinator, message broker, or
event-sourcing framework, per `ROADMAP.md` § "Deliberate non-goals." `StatesmanRemoteClient`
remains an operations client, not a transparent distributed `IState<T>` proxy
(`docs/guides/hosting.md:36`) — nothing in this design changes that boundary.

## Addendum (pre-Phase-2, 2026-09-03)

Phase 2 planning research found the original Phase 2 design above (a generic decorator over
`ReadHistoryAsync`) was not feasible as specced — `ReadHistoryAsync` is single-stream, and a change
feed is a cross-stream query only EF Core's schema already supports. Presented to the user as a
genuine scope decision (full per-provider native cross-stream indexing vs. a cheaper but
structurally-incomplete runtime-layer merge over already-observed addresses vs. reordering Phase 3
ahead of Phase 2): **full per-provider native implementation was chosen**, recorded in the revised
Phase 2 section above. This turned out to also simplify the design: no resolution-time decorator
means no need for that decorator to separately implement `IStateCapabilityProvider`, which removes
the interaction risk this document's Phase 1 addendum had flagged.

## Addendum (post-Phase-2, 2026-09-03)

Phase 2's final whole-branch review found two Critical, cross-provider issues that no single
per-task review could see (each only looked at one provider). Both were real. One was fixed before
merge; the other is a genuine design gap, documented here rather than papered over, because the
still-unplanned `IStateChangeNotifier` half of this phase and any future outbox adapter (Phase 7)
depend on knowing exactly what guarantee this feed does and doesn't make.

**Fixed before merge, verified directly (not just claimed):** `TieredStateLedgerStore`'s default
`ReadMode` (`ValidateCold`) calls `ImportAsync` on the hot replica on every read that hits cold, and
`ImportAsync` was unconditionally appending to the change feed on InMemory and FileSystem — turning
ordinary reads through the default tiered configuration into an unbounded feed-growth leak.
Confirmed empirically, not just by reading the diff: temporarily reverting the `isNewPosition` guard
and re-running the regression test showed a triple `ImportAsync` of the same record producing three
change-feed entries instead of one. Both providers now only append when the import genuinely
introduces a new `GlobalPosition`, and both gained a regression test pinning this.

(The controlling session briefly and incorrectly concluded, mid-session, that this finding was a
"false positive": it lost track of an already-running fix-wave agent across a context-compaction
event, read that agent's uncommitted in-progress edit off the shared working-tree disk, and mistook
it for pre-existing history — then wrote that incorrect conclusion into the spec and dispatched a
second, different fix-wave agent for a narrower scope (a real `ReadAsync` file-sharing fix and a
real `CancellationToken.None` fix, both independently verified against the code and genuinely
needed — see below) without realizing the first agent was still active on the same file. Both
agents' edits were real, not fabricated, and turned out to be compatible; the second agent's edits
were deliberately reverted, not because they were wrong, but to let the first agent land its
already-further-along, independently-verified fix cleanly first — the second agent's fixes were
redone against that clean baseline afterward. Recorded here as a process note: losing track of
a long-running background agent across compaction, then re-deriving conclusions from a shared
working tree without checking who else might be mid-edit on it, produced a confidently-wrong
"already correct" claim — verify empirically and account for concurrent agents before writing a
correction into permanent documentation.)

**Not fixed, tracked as an open design question — resolve before building anything on top of this
feed:** `GlobalPosition` is allocated before the record is durably visible on four of five
providers (Redis: `INCR` then a transaction round-trip later; FileSystem: an in-memory counter then
two fsync'd writes later; InMemory: `Interlocked.Increment` then an enqueue moments later — only EF
Core allocates and commits the position inside the same transaction). A consumer reading while
position *N*'s append is still in flight but *N+1*'s has already landed sees only *N+1*, persists
that as its cursor, and can never see *N* — it will land below the consumer's watermark on the next
read. This is the standard change-data-capture "low water mark" problem, and as shipped, none of
`IStateChangeFeed`'s doc comment, the provider docs, or the tests say the feed can do this.

A real fix is either a stability window (only yield positions older than some settle interval, or
below the lowest currently-in-flight position — needs each provider to track in-flight allocations)
or moving position allocation to commit time everywhere (which EF Core already does, but doing the
same for Redis/FileSystem/InMemory means giving up the per-address write concurrency those
providers currently have — a real trade-off, not a small patch). Until one of these ships:
`IStateChangeFeed` consumers must treat the feed as **at-least-once with possible tail loss under
concurrent writes to different addresses**, not lossless — the spec's "push accelerates, feed is
authoritative" framing for `IStateChangeNotifier` (below) needs to be revisited against this before
that follow-on plan is written.

**Also flagged by the same review, lower priority, tracked but not blocking:**
- **Retention/prune interaction is inconsistent and mostly undefined.** Pruning a stream deletes
  it from `ReadHistoryAsync` but each provider's change feed reacts differently: EF Core's feed
  silently loses the pruned records (it queries the same table `PruneAsync` deletes from);
  FileSystem's index file keeps a now-dangling line forever (silently skipped on read, never
  cleaned up); Redis's and InMemory's change-feed structures aren't trimmed at all and retain
  everything forever regardless of the store's own retention policy — for InMemory this is a real
  regression, since `MaxRevisions`/`MaxBytes` existed specifically to bound memory and the change
  feed now defeats that bound. Needs a decided, documented, and provider-consistent semantic (own
  follow-up).
- **`TieredStateLedgerStore` advertises `IStateChangeFeed` even in a hypothetical composition where
  its cold store couldn't back it** — `TryGetCapability<T>`'s direct-cast-first behavior means
  capability negotiation says yes unconditionally, and only a `NotSupportedException` on the first
  actual read would reveal a real gap. Not reachable with any of today's five providers (all
  implement the capability), but the same shape will recur for `IPartitionCatalog` (Phase 3) and
  needs an architectural answer then: either let `IStateCapabilityProvider` veto a direct cast, or
  have `TryGetCapability<T>` consult the provider before the cast when a store implements both.
- **No paging/batch limit on `IStateChangeFeed.ReadAsync`.** Only EF Core streams the underlying
  query; Redis and InMemory materialize the full since-cursor result before yielding. FileSystem
  already avoids the worse version of this — it sorts lightweight `(position, address, revision)`
  tuples first and re-reads each full record lazily inside the yield loop
  (`FileSystemStateLedgerStore.cs:294-338`), so it only holds the small tuples in memory, not full
  deserialized records — but it still reads the entire index file per call regardless of cursor. A
  consumer resuming after being offline a long time — the primary use case for a durable feed —
  pulls its entire backlog into memory in one call today. Worth deciding
  before any external consumer exists, since adding a batch parameter to a shipped capability
  interface later is a breaking change.
- `StateChangeCursor` carries no store identity, so a cursor obtained from one store can be passed
  to a different store's `ReadAsync` with no error, silently returning the wrong slice. Consider a
  store fingerprint if this proves to be a real footgun in practice.

**Genuinely fixed, empirically verified (commit `e37b4a7`):** `FileSystemStateLedgerStore.ReadAsync`
was not taking `_changeFeedGate` before reading the index file — the same gate
`AppendChangeFeedEntryAsync` already holds while writing to it — a real Windows file-sharing race
(broader than the Task 5 per-task review's "narrow Import-repair" framing: any concurrent read plus
any write). `ReadAsync` now acquires the gate around the file-exists check, read, and line-parsing
loop, releasing it before the second loop that does the actual yielding. A concurrent
`AppendAsync`/`ReadAsync` stress test reliably reproduced the exact pre-fix `IOException` (5/5 manual
runs against the unpatched code) and now passes consistently. `AppendAsync`/`ImportAsync` were also
passing the caller's `CancellationToken` into the change-feed append after the primary record write
had already durably committed — a cancellation in that narrow window made an already-successful
write look like it failed to the caller — both call sites now use `CancellationToken.None` for that
specific, already-committed-work append.

These caveats belong in `docs/providers/index.md`'s change-feed section (added as part of this
phase's final fix wave) so they're discoverable by users, not just by whoever reads this spec.
