# ROADMAP 0.3: durable distributed coordination — design

Status: approved for spec review
Date: 2026-09-03
Scope: all eight items listed under `ROADMAP.md` § "0.3: durable distributed coordination"

## Problem

Statesman's core ledger contract (`IStateLedgerStore`, `src/Statesman.Abstractions/Ledger.cs:221`) is
deliberately process-local: `AppendAsync` gives per-address optimistic concurrency
(`StateWriteCondition`, `Ledger.cs:171`) and nothing more. Every distributed guarantee the docs
gesture at — cross-process coherent capture, leader election for maintenance workers, durable
resumable change feeds, partition enumeration, replication-lag visibility, portable
import/export, and outbox delivery — is either absent or implicitly scoped to a single process,
and the docs say so explicitly (see the exhaustive gap inventory this design is based on, captured
in this session's background research). `ROADMAP.md` groups these eight gaps as milestone 0.3 with
one exit criterion:

> no distributed method silently falls back to process-local semantics; capability discovery
> tells callers exactly which guarantee is available.

This document designs how all eight items get built coherently, on one shared mechanism, rather
than as eight unrelated features.

## Grounding: what exists today

- `IStateLedgerReplica` (`Ledger.cs:248`) is a one-member optional interface (`ImportAsync`) that a
  store implements only if it can accept exact records. Consumers discover it via `as`/`is`. This
  is the **only** capability-negotiation precedent in the codebase — there is no descriptor,
  registry, or `Supports(...)` method anywhere else in `src/`.
- `StateRecord` carries `Revision` (per-address) and `GlobalPosition` (store-wide,
  `Ledger.cs:16`) as separate fields. Redis assigns `GlobalPosition` via `INCR` *before* the
  conditional write commits (`RedisStateLedgerStore.cs:119`), so position is consumed even on a
  failed CAS — `GlobalPosition` is monotonic but **sparse**, never a count.
- `StatesmanRuntime.CaptureAsync` (`StatesmanRuntime.cs:160`) takes an in-process `CommitGate`
  semaphore before computing a snapshot's position — the "coherent capture" guarantee is scoped to
  that gate's process lifetime, nothing more.
- `StatesmanHostedService.ExecuteAsync` (`StatesmanHostingExtensions.cs:72`) runs a `PeriodicTimer`
  and calls `root.MaintainAsync` on every tick, in every process, with no coordination.
- `StateChangeHub<T>` (`StateChangeHub.cs`) is a live, in-memory, bounded/drop-oldest fanout
  (`Channel.CreateBounded(..., FullMode = DropOldest)`) — by design not durable (ADR 0004:
  "observation is not delivery").
- No shared provider conformance suite exists yet (ROADMAP 0.2 item, still aspirational). Each
  provider has its own test project under `tests/`.
- Provider-side primitives found: FileSystem uses per-address `SemaphoreSlim`s (in-process only,
  no cross-machine lock); Redis has the `GlobalPosition` counter but no lock/lease primitive
  in-code; Tiered has read-mode policy knobs (`PreferHot`, `ServeHotWhenColdUnavailable`) but no
  lag metadata field on any type; EF Core has no distributed primitive found.

## Architecture: one capability-negotiation convention for all eight items

Added to `Statesman.Abstractions` (Phase 0, shipped):

```csharp
public interface IStateCapability { }

public static class StateCapabilityExtensions
{
    public static bool TryGetCapability<TCapability>(
        this IStateLedgerStore store,
        [NotNullWhen(true)] out TCapability? capability)
        where TCapability : class, IStateCapability
    {
        capability = store as TCapability;
        return capability is not null;
    }
}
```

`IStateLedgerReplica` is retrofitted to extend `IStateCapability` so the existing precedent and all
new capabilities share one idiom. No registry, no descriptor object — a provider either implements
the interface or it doesn't, so the capability surface can never drift from what is actually
implemented (enforced by a reflection-based completeness test, see Testing). Every new distributed
capability below is `I<Name> : IStateCapability`, discovered exclusively through
`TryGetCapability`. `[NotNullWhen(true)]` is required on the `out` parameter — without it, the
documented `if (store.TryGetCapability(out X? x)) { x.Method() }` pattern fails to compile cleanly
under this repo's `TreatWarningsAsErrors=true` (CS8602).

`docs/architecture/capabilities.md` (new) becomes the single table of capability interface ×
provider, kept honest by a conformance test (see Testing) that asserts the doc matches
`TryGetCapability` results at runtime.

### Capability forwarding through wrapping stores

`TryGetCapability` is a plain `as` cast on the concrete store. `TieredStateLedgerStore` wraps a hot
and a cold `IStateLedgerStore` without implementing any capability itself, so a Tiered store over a
Redis hot tier would report `TryGetCapability<IStateLeaseProvider>() == false` in Phase 1 even
though a lease provider exists one level down — same problem for Phase 2's `IStateChangeNotifier`.
(Phase 5's `IReplicationLagSource` is unaffected: Tiered implements that one itself, since lag is a
property of the tiering relationship, not something to forward.)

Resolution: an opt-in escape hatch, consulted only after the direct cast fails, so it changes
nothing for any store that doesn't implement it:

```csharp
public interface IStateCapabilityProvider
{
    bool TryGetCapability(Type capabilityType, out object? capability);
}
```

`TryGetCapability<TCapability>` tries the direct cast first; on failure, if the store implements
`IStateCapabilityProvider`, it consults that and casts the result. `TieredStateLedgerStore` adopts
`IStateCapabilityProvider` in whichever phase first ships a capability it needs to forward (Phase 1
for leases) — delegating to whichever of its hot/cold stores can back the request, per that phase's
own policy for which tier is authoritative. This is source- and binary-compatible to add once and
does not need revisiting per phase.

#### Forwarding policy (decided before Phase 7, 2026-09-05)

"Per that phase's own policy" was left undefined for five phases and is now written down, because
omission is how the `IStateLedgerReplica` bug shipped. `TieredStateLedgerStore` decides per
capability, and the decision follows from what the capability *does*, never from a default. Four
classifications, exhaustive:

- **Authoritative write — vetoed, never forwarded.** A capability whose operations put records into
  the ledger (`IStateLedgerReplica` today). The hot store is the tiered store's private cache-repair
  channel; forwarding write authority to it lets records land in the cache that the cold authority
  never sees, which is exactly what let a `Statesman.Tooling` restore write into the cache in Phase
  6. `TryGetCapability` returns `false` for these *before* any forwarding attempt. Callers needing
  such a capability resolve the cold store and target it directly.
- **Authoritative read over ledger contents — implemented on Tiered, delegated to cold.**
  `IStateChangeFeed`, `IPartitionCatalog`, `IDistributedCapture`, `IStateChangeNotifier`.
  Implemented directly on `TieredStateLedgerStore`, delegating to `_cold` and throwing
  `NotSupportedException` naming the
  cold tier when cold cannot back it. They never reach the generic forwarder, so discovery succeeds
  unconditionally on a tiered store and the honest answer arrives at first use rather than at
  discovery.
- **Coordination rather than data — forwarded hot-first.** `IStateLeaseProvider`. Contention happens
  where the hot tier is, and a lease says nothing about ledger contents, so the generic forwarder's
  hot-then-cold order is correct here. This is the one class the generic forwarder is *for*.
- **A property of the tiering relationship itself — Tiered-only.** `IReplicationLagSource`.
  Implemented by `TieredStateLedgerStore` alone; neither forwarded nor delegated, because no single
  tier can answer it.

**Every new capability must be classified into one of these four before it ships, and the
classification is what a phase's pre-flight scan records.** Inheriting the generic forwarder's
hot-first default by omission is how the `IStateLedgerReplica` bug shipped; a capability with no
recorded classification is an unreviewed decision, not a neutral one.

### Signaling convention

Every capability-gated call site follows one of two documented behaviors — decided per capability
below, never improvised per call site:

- **(a) Documented degradation**: `TryGetCapability` returns false → the caller runs its existing
  process-local behavior and logs a defined event noting distributed coordination is unavailable.
  Used only where the degraded behavior is safe and was already the pre-0.3 behavior (e.g.
  maintenance workers without a lease provider).
- **(b) Hard failure**: `TryGetCapability` returns false → the caller throws
  `NotSupportedException` naming the missing capability. Used wherever silently returning a
  weaker guarantee than requested would be incorrect (e.g. distributed capture must never
  quietly return a process-local snapshot).

## Phases

Phases are dependency-ordered; each is one PR-sized (or small PR series) unit landing on `main`
with green CI before the next begins.

### Phase 0 — Foundation (shipped)

`IStateCapability`, `TryGetCapability<T>`, retrofit `IStateLedgerReplica`, add
`docs/architecture/capabilities.md` backed by a reflection-based completeness test. No provider
behavior change. Unblocks every later phase. Landed on `main` 2026-09-03. `IStateCapabilityProvider`
(capability forwarding, above) was designed during this phase's final review; it shipped in Phase 1,
its first consumer (`TieredStateLedgerStore` forwarding `IStateLeaseProvider`).

### Phase 1 — Leases (`IStateLeaseProvider`) (shipped)

```csharp
public interface IStateLeaseProvider : IStateCapability
{
    ValueTask<IStateLease?> AcquireAsync(string leaseId, TimeSpan ttl, CancellationToken ct);
}

public interface IStateLease : IAsyncDisposable
{
    ValueTask<bool> RenewAsync(TimeSpan ttl, CancellationToken ct);
}
```

- **Redis**: `SET NX PX` to acquire, Lua compare-and-delete to release. Single-instance
  consistency only — documented as such, not Redlock/quorum.
- **EF Core**: a lease row with an expiry column, acquired via an optimistic conditional update.
  Expiry is evaluated against the acquiring process's own clock, not enforced server-side (unlike
  Redis's TTL) — clock skew between replicas is a real, if small at a 30s TTL, property of this
  provider's mutual exclusion.
- **FileSystem, in-memory**: do not implement it (consistent with the existing "don't point
  multiple writers at a shared network directory" caveat, `docs/providers/index.md:21`).
- Leasing lives in `StatesmanRuntime.MaintainAsync`, not `StatesmanHostedService`: `IStatesman`
  (the public interface `StatesmanHostedService` holds) exposes no store reference, and a single
  root is not backed by one store — each `StateHandle<T>` resolves its own store independently via
  `Manifest.Store`, a plain string, so different state keys under the same root can live in
  different stores. `MaintainAsync` groups its due handles by `Manifest.Store`, resolves each named
  store, and acquires a lease per group (`$"{Id}:{storeName}:maintenance"`, where `Id` is the
  declaration's stable root name, not a per-process id) before refreshing that group when the store
  supports leases; falls back to today's per-process behavior, tracked internally (mirroring the
  existing `MaintenanceFailures` pattern, not a new logging dependency) when it doesn't. This is
  signaling case (a). `StatesmanHostedService` itself is unchanged. (This corrects the mechanism
  placement originally specced above; caught during Phase 1's Task 2 review, 2026-09-03.)
- `TieredStateLedgerStore` implements `IStateCapabilityProvider` (shipped in Phase 1, not deferred
  to when Phase 1 needed it as originally noted above — it was Phase 1 that needed it), forwarding
  to whichever of its hot/cold stores implements `IStateLeaseProvider` (hot first, since hot is
  where maintenance contention actually happens). **Open design question, still live:** this
  hot-first forwarding is currently unconditional for *every* capability type, not just leases —
  correct for leases, but would be wrong for an authoritative-store-shaped capability discovered
  *through* this forwarding path (cold, typically, should win for those). Resolved for
  `IStateChangeFeed` specifically in Phase 2 below — it turned out not to need Tiered's forwarding
  at all, since every provider implements it directly and Tiered delegates straight to cold like
  `ReadHistoryAsync` already does. The general policy question remains open for whatever capability
  next relies on `IStateCapabilityProvider` forwarding through Tiered (e.g. Phase 4's distributed
  capture) — resolve it then, don't inherit hot-first by accident.
- **Not implemented in Phase 1, tracked for a hardening pass:** `IStateLease.RenewAsync` exists and
  is implemented/tested by both providers but has no production caller — the fixed 30s
  `MaintenanceLeaseTtl` is a hard cap with no renewal, so a refresh that runs longer than 30s loses
  its exclusion guarantee mid-flight. A shared conformance suite per capability interface (see
  Testing, below) was also deferred to when a third provider exists; in the meantime both Redis and
  EF Core cover acquire/deny/expire/renew but not the specific property that a stale (already
  superseded) lease holder's `DisposeAsync` must not release/renew a *successor's* lease — this is
  the safety property the whole feature rests on and should not go untested indefinitely.

### Phase 2 — Durable change feed (shipped) + provider-native notifications

```csharp
public interface IStateChangeFeed : IStateCapability
{
    IAsyncEnumerable<StateChangeEnvelope> ReadAsync(StateChangeCursor? from, CancellationToken ct);
}
```

**Revised after Phase 2 research, 2026-09-03 (see Addendum below for why):** this is NOT built as a
generic decorator over `ReadHistoryAsync`. `ReadHistoryAsync` is scoped to one already-known
`StateAddress` (`Ledger.cs:238-241`); a change feed needs to discover records across *every*
address in a store since a cursor — a fundamentally different query shape only EF Core's existing
schema supports natively (its `StatesmanRecords` table has a real, unique-indexed `GlobalPosition`
column spanning every stream). Redis, FileSystem, and in-memory have no such cross-stream index
today.

Each provider implements `IStateChangeFeed` **directly and natively**, doing real cross-stream
work:
- **EntityFrameworkCore**: `SELECT * FROM StatesmanRecords WHERE GlobalPosition > @cursor ORDER BY
  GlobalPosition` against the existing indexed column — no schema change needed.
- **Redis**: a new global sorted set (`{prefix}:{name}:changes`, scored by `GlobalPosition`,
  storing the serialized record directly, mirroring the existing per-stream history sorted set's
  storage shape) populated by an additional write inside `AppendAsync`'s existing transaction.
  `ReadAsync` is `SortedSetRangeByScoreAsync` with an exclusive lower bound at the cursor.
- **FileSystem**: a single append-only global index file, written under its own lock alongside
  each `AppendAsync`, storing `{position}\t{address.Canonical}\t{revision}` per line; `ReadAsync`
  scans forward from the cursor and re-reads each referenced record from the existing per-address
  storage. Not optimized (an O(appends-since-cursor) scan) — acceptable for now, and a natural
  candidate for ROADMAP 0.2's still-unbuilt "filesystem recovery and compaction tooling" to
  optimize later with a real index, not a scope concern for Phase 2.
- **In-memory**: a `List<StateRecord>` (or equivalent) appended to under the existing per-stream
  gate's sibling lock, alongside `_streams`; already naturally position-ordered.
- **Tiered**: delegates directly to `_cold`'s `IStateChangeFeed` — the ledger's authoritative
  source, matching `TieredStateLedgerStore.ReadHistoryAsync`'s existing (and correct) behavior of
  always reading history from cold regardless of `ReadMode` (`TieredStateLedgerStore.cs:88-95`).

This resolves the capability-forwarding risk the Phase 1 addendum flagged for this exact
capability: there is no resolution-time decorator, so there is nothing that needs to *also*
implement `IStateCapabilityProvider` to keep other forwarded capabilities (like leases) working
through it. `IStateChangeFeed` is discovered exactly like any other Phase 0-style capability —
`TryGetCapability<IStateChangeFeed>` — and, because every provider implements it directly under
this design, it is universal in effect without being architecturally special-cased. A provider that
can't back it (none currently) would report unsupported honestly (signaling case (b)) rather than
silently degrading through a generic adapter.

`StateChangeCursor` opaquely wraps a store's `GlobalPosition`; it is never treated as a count or
used arithmetically by callers, only round-tripped. `StateChangeEnvelope` carries the `StateRecord`
plus the `StateChangeCursor` to resume from after it.

`IStateChangeNotifier : IStateCapability` (Redis pub/sub) is a genuinely optional low-latency push
hint that `StateChangeHub` may subscribe to, but any consumer needing correctness must still
reconcile through `IStateChangeFeed` — push accelerates, feed is authoritative. This preserves ADR
0004's boundary: notification is still not delivery; the feed is what makes delivery durable. **Shipped
as Phase 9; see below.**

### Phase 3 — Partition discovery (`IPartitionCatalog`)

```csharp
public interface IPartitionCatalog : IStateCapability
{
    IAsyncEnumerable<StatePartitionDescriptor> ListPartitionsAsync(CancellationToken ct);
}
```

Implementable by all five current providers (InMemory, FileSystem, Redis, EF Core, Tiered) — the
roadmap's "for stores that can support it efficiently" hedge does not exclude any shipped provider
today.

**Corrected during Phase 3 planning, 2026-09-04:** the specific per-provider mechanisms first
sketched above (FileSystem directory enumeration, Redis `SCAN` by key pattern, EF Core
`SELECT DISTINCT`) turned out not to work as stated — a pure technical correction, not a
completeness/cost trade-off, so resolved directly rather than put to the user (matching the Phase 1
lease-mechanism-placement precedent). Both FileSystem's per-address directories and Redis's
per-stream keys are SHA-256 hashed (`FileSystemStateLedgerStore.StreamDirectory`,
`RedisStateLedgerStore.StreamKey`), so neither a directory walk nor a key-pattern `SCAN` can recover
the original `StateAddress` at all — not merely inefficient, genuinely impossible. The actual plan:
FileSystem reuses Phase 2's existing plaintext `_changes.log` (which already carries full address
components per line); Redis adds a small new Hash (`{prefix}:{name}:partitions`) written inside the
same `AppendAsync` transaction that already writes the Phase 2 change-feed sorted set — the same
"add a native per-provider index" pattern Phase 2 already established, not a new architectural
choice. EF Core doesn't need `SELECT DISTINCT` at all: its existing `StatesmanHeads` table already
holds exactly one row per partition (it's the head/latest-revision table), so `ListPartitionsAsync`
is a plain `AsNoTracking()` enumeration of it, cheaper than scanning `StatesmanRecords`. See
`docs/superpowers/plans/2026-09-04-roadmap-0.3-phase-3-partition-catalog.md` for the exact code.

### Phase 4 — Distributed coherent capture (`IDistributedCapture`)

```csharp
public enum StateCaptureConsistency { ProcessLocal, ReadCommittedDistributed, SnapshotDistributed }

public interface IDistributedCapture : IStateCapability
{
    ValueTask<StateSnapshotSet> CaptureAsync(
        IEnumerable<StateReference> references, StateCaptureConsistency required,
        StateReadOptions? options, CancellationToken ct);
}
```

Only providers that can back a real cross-process guarantee implement it — EF Core via a
serializable transaction, Redis via `MULTI`/`EXEC` best-effort. FileSystem does not implement it.
Requesting a consistency level a provider can't back, or calling on a provider without the
capability at all, is signaling case (b): `NotSupportedException`, never a silent process-local
capture returned as if it were distributed.

**Corrected during Phase 4 planning, 2026-09-04:** the interface as first sketched above takes
`StateReference`, but `StateReference` (`Identity.cs:139`) has no `Root` — it identifies a declared
state within one already-known `IStatesman` root, not a store-level address, and a single store can
back multiple roots. The store-level capability actually takes `StateAddress`
(`Identity.cs:118`, the type every other store-facing method already uses):

```csharp
public interface IDistributedCapture : IStateCapability
{
    ValueTask<IReadOnlyDictionary<StateAddress, StateRecord?>> CaptureAsync(
        IEnumerable<StateAddress> addresses, StateCaptureConsistency required, CancellationToken ct);
}
```

**A second, related correction:** the store-level method also drops `StateReadOptions` and does not
return `StateSnapshotSet` — both are runtime-shaped concerns the store has no way to honor.
`StateReadOptions` (`Cached`/`Current`/`Fresh`) governs per-handle cache freshness, a concept that
only exists at the runtime/handle layer (`IStateHandleInternal.GetUntypedAsync`); a store-level
capture is inherently a fresh, current read of the ledger, like `ReadLatestAsync` (which itself
takes no `StateReadOptions` either). And building an `IStateSnapshot` requires deserializing
`StateRecord.Payload` against a specific CLR type, migration table, and `IStateSerializer` — all
runtime/declaration concerns (`RuntimeDefinition.cs:70-122`) a store has neither access to nor any
business performing. The store-level capability therefore returns raw, per-address
`StateRecord?` (mirroring `IStateLedgerStore.ReadLatestAsync(StateAddress, ct) : StateRecord?`,
generalized to many addresses read coherently in one call; `null` per address means "no record yet",
same as `ReadLatestAsync`), and the *runtime* converts each into a typed `IStateSnapshot` via the
already-existing internal `IStateRuntimeDefinition.CreateSnapshot(address, record, serializer,
observedAt)` (`RuntimeDefinition.cs:16-20,63-68`) — the same method `StateHandle<T>` already uses
internally, just invoked directly instead of through a handle's cached state.

`StateSnapshotSet` and the runtime-level, `StateReference`-based `IStatesman.CaptureAsync` /
`IStateContainer.CaptureAsync` already exist and ship today (`RuntimeContracts.cs:126,183`,
implemented in `StatesmanRuntime.CaptureAsync`, `StatesmanRuntime.cs:164-196`) — that existing
implementation (hydrate each handle, take the in-process `CommitGate`, snapshot
`CurrentUntyped`) *is* today's `StateCaptureConsistency.ProcessLocal`, just not yet named as a level.
Phase 4 adds a `StateCaptureConsistency required = ProcessLocal` parameter to the runtime-level
methods, inserted right after `references` so `CancellationToken` stays the last parameter (default
preserves today's behavior; the one existing 3-positional-argument call site,
`StateFixture.cs:115`, moves to named arguments rather than relying on position) rather than
inventing a second capture path: when a distributed level is requested, `StatesmanRuntime.CaptureAsync`
groups the requested handles by resolved store (same `GroupBy(handle => handle.Manifest.Store)` shape
`MaintainAsync` already uses for lease grouping, `StatesmanRuntime.cs:312`), resolves each group's
store, calls `TryGetCapability<IDistributedCapture>()` per store, calls its `CaptureAsync` with just
that group's addresses, merges the returned per-address `StateRecord?`s across groups, and builds the
final `StateSnapshotSet` by running each requested handle's address and its resolved record through
`IStateRuntimeDefinition.CreateSnapshot` — throwing `NotSupportedException` (case (b)) if any group's
store lacks the capability, never falling back to `ProcessLocal` silently. (`StateCaptureConsistency`
itself is not re-validated by the runtime beyond routing — each store's own `CaptureAsync`
implementation is responsible for rejecting a level it personally cannot back.)

Per-provider mechanism, corrected against the actual client APIs:
- **EF Core**: reuses the transaction pattern `AppendAsync`/lease `AcquireAsync` already use
  (`context.Database.BeginTransactionAsync(IsolationLevel, ct)`,
  `EntityFrameworkStateLedgerStore.cs:133-135,221-223`) — open one transaction, read every requested
  address's `StatesmanHeads` row inside it, commit. `ReadCommittedDistributed` and
  `SnapshotDistributed` map to real, different isolation levels (`ReadCommitted` vs. `Serializable`)
  on the same one transaction-per-call shape — an honest, not cosmetic, distinction.
- **Redis**: the spec's original "`MULTI`/`WATCH`" phrasing is corrected — `WATCH` is a
  write-conflict-detection primitive and has no role in a pure read. The actual mechanism is an
  unconditional `MULTI`/`EXEC` batch of `StringGetAsync(HeadKey(address))` per requested address
  (same `ITransaction` API `AppendAsync` already uses for its conditional writes,
  `RedisStateLedgerStore.cs:141-162`, just without `AddCondition` since nothing is being compared).
  On standalone Redis, command execution is single-threaded, so a `MULTI`/`EXEC` batch is a true,
  exact atomic snapshot, not merely "best-effort" — `ReadCommittedDistributed` and
  `SnapshotDistributed` are not distinguishable on this provider and should be accepted and honored
  identically by the same one code path, rather than built as two. The real best-effort boundary is
  **Redis Cluster**: addresses whose keys land in different hash slots can't share one `MULTI`/`EXEC`
  (`CROSSSLOT`), so a cluster-mode capture spanning slots must throw `NotSupportedException` rather
  than silently degrading to unsynchronized sequential `GET`s.
- **FileSystem**: confirmed to have no cross-process, multi-file transactional primitive at all
  (its gates are in-process `SemaphoreSlim`s only) — "does not implement it" stands as specced, same
  rationale as Phase 1's lease non-implementation.
- **Tiered**: implements `IDistributedCapture` directly and delegates straight to `_cold`, throwing
  `NotSupportedException` if cold lacks it — the same pattern `IStateChangeFeed` and
  `IPartitionCatalog` already established (`TieredStateLedgerStore.cs:104-121`), not generic
  `IStateCapabilityProvider` forwarding. This is correct, not just consistent: capture's entire
  purpose is a coherent guarantee over the *authoritative* store, and hot is explicitly
  non-authoritative everywhere else in this codebase. It also means this is the third consecutive
  capability (after the change feed and partition catalog) to sidestep the open
  hot-first-forwarding-policy question from the Phase 1 addendum by being implemented directly on
  Tiered — that general policy question can stay deferred; no shipped capability actually depends on
  it today.

**Also resolved in this phase, not parked a second time:** the Phase 1 addendum's parked EF Core
lease race. `AcquireAsync` (`EntityFrameworkStateLedgerStore.cs:211-251`) opens its transaction,
checks for an existing unexpired lease, then `Add`s or updates a row and calls
`SaveChangesAsync`/`CommitAsync` **with no `catch` at all** — unlike `AppendAsync`, which wraps the
same shape in `catch (DbUpdateException)` and reconciles (`EntityFrameworkStateLedgerStore.cs:196-208`).
Two concurrent first-acquisitions both observe no existing row, both `Add` a row with the same
`LeaseId` primary key, and the loser's `SaveChangesAsync`/`CommitAsync` throws an uncaught
`DbUpdateException` (PK violation) instead of `AcquireAsync` returning `null` — the interface's own
documented "someone else got it" outcome (`Ledger.cs:270-274`). Phase 4 fixes this by mirroring
`AppendAsync`'s existing catch/rollback/re-read pattern exactly, since Phase 4's own EF Core work
depends on the same transaction-retry-on-conflict shape for capture.

### Phase 5 — Replication lag metadata (`IReplicationLagSource`)

```csharp
public interface IReplicationLagSource : IStateCapability
{
    ValueTask<StateReplicationLag> EstimateLagAsync(CancellationToken ct);
}
```

Implemented by `Statesman.Persistence.Tiered`, comparing hot vs. cold `GlobalPosition`. Feeds the
0.2 OpenTelemetry semantic-conventions work as an additional metric source.

**Refined during Phase 5 planning (2026-09-04), verified against current code:** the sketch above is
feasible as written, but "comparing hot vs. cold `GlobalPosition`" needs a concrete source for each
tier's newest position, and `IStateLedgerStore` has no such member. Phase 3's `IPartitionCatalog`
is that source: every provider yields one `StatePartitionDescriptor` per partition whose
`LastPosition` is that partition's head `GlobalPosition`, and `IStateLedgerReplica.ImportAsync`
preserves `GlobalPosition` exactly on every replica (InMemory, FileSystem, and EF Core each advance
their own counter to the imported position rather than re-allocating), so a hot head at the same
position as its cold head is genuinely the same record. Tiered therefore estimates lag by
enumerating **hot's catalog first, then cold's** (so an authoritative write landing mid-estimate can
only over-report lag, never under-report it), and reports:

```csharp
public sealed record StateReplicationLag
{
    public required long AuthoritativePosition { get; init; } // cold's newest head position, 0 when empty
    public required long ReplicaPosition { get; init; }       // hot's newest head position, 0 when empty
    public required int PartitionsBehind { get; init; }       // cold partitions hot lacks or holds at an older position
    public long PositionGap => Math.Max(0, AuthoritativePosition - ReplicaPosition);
    public bool IsCaughtUp => PartitionsBehind == 0 && PositionGap == 0;
}
```

Consequences worth stating plainly: (1) both tiers must implement `IPartitionCatalog` or
`EstimateLagAsync` throws `NotSupportedException` (case (b)) — true of all five shipped providers;
(2) `PositionGap` is a distance in a **sparse** sequence (Redis consumes a position on a failed
CAS), never a record count; (3) the hot tier is populated lazily by reads and writes routed through
the tiered store, so `PartitionsBehind` counts partitions the replica has simply never been asked
for as well as ones it holds stale — this is honest for a replica-lag metric and is documented,
not hidden; (4) the estimate's cost is one catalog enumeration per tier, which on FileSystem is
O(total writes) (Phase 3's documented cost) — acceptable for a polled metric, not for a hot path;
(5) `EstimateLagAsync`'s token gets the `= default` every other capability method in `Ledger.cs`
has, a cosmetic deviation from the sketch. No metric instrument is registered in this phase:
`StatesmanTelemetry`'s `Meter` is synchronous-callback (`ObservableGauge`) territory and catalog
enumeration is async, so the capability ships as the pollable source the 0.2 telemetry work can
sample from a hosted loop later, rather than a half-wired gauge now.

### Phase 6 — Import/export/restore tooling

New library (`Statesman.Tooling`, name TBD at plan time) built on the existing
`IStateLedgerReplica.ImportAsync`. Export format carries the declaration fingerprint and a schema
version; restore validates both against the target's current fingerprint before importing, and
refuses (case (b)) on mismatch rather than importing incompatible history.

#### Refined during Phase 6 planning (2026-09-04)

Planning research verified the sketch above against the code and refined it in four places. The
user was consulted (`AskUserQuestion`) on the first three; the fourth is a planning ruling.

- **Redis gains `IStateLedgerReplica`.** The sketch builds restore on `ImportAsync`, but Redis was
  the one non-tiered provider without it (`docs/architecture/capabilities.md`). Nothing structural
  prevents it: `RedisStateLedgerStore.AppendAsync` already writes head, revision guard, history
  sorted set, change-feed sorted set, and partition hash inside one `MULTI`/`EXEC`, so an exact import
  is the same transaction shape keyed by the record's own `Revision`/`GlobalPosition`, plus a
  max-advance of the `global-position` counter (a small Lua script, run *before* the transaction so
  no concurrent append can ever allocate a position at or below the imported one). The alternative —
  restore refusing Redis with `NotSupportedException` — would have left a "No" cell that reflects
  missing work rather than a genuine limitation, which the capability convention is meant to avoid.
  Restore therefore works on every shipped provider except Tiered (restore into its cold store
  directly; Tiered deliberately does not implement `IStateLedgerReplica` because cold is
  authoritative). Redis also becomes eligible as a Tiered hot tier.
- **Export reads `IPartitionCatalog` + per-partition `ReadHistoryAsync`, not `IStateChangeFeed`.**
  The feed is documented at-least-once with possible tail loss under concurrent writes (post-Phase-2
  addendum) and its prune interaction is provider-inconsistent (Redis/InMemory retain pruned records
  forever, EF Core loses them). Enumerating the catalog (every shipped provider has one), filtering to
  the manifest's root, sorting partitions by `Canonical`, and streaming each partition's full history
  oldest-first gives an export that is complete for every *retained* revision, deterministic in
  layout, streamable without materializing, and free of both feed caveats. What it is **not** is a
  cross-partition point-in-time snapshot: a write concurrent with the export may or may not appear,
  per partition. The documented promise is therefore "every revision the source retains for every
  partition its catalog lists under this root, each partition read atomically-enough for its own
  provider; quiesce writers for a consistent backup." Implementation trap found: `StateHistoryOptions`
  defaults `Take` to 100 and `NewestFirst` to true — export must pass `Take = null, NewestFirst = false`
  explicitly or silently truncate long histories.
- **Package name is `Statesman.Tooling`** (the sketch's suggestion), namespace `Statesman.Tooling`,
  depending only on `Statesman.Abstractions`. Public surface: `StateLedgerExport.ExportAsync` /
  `ExportToFileAsync`, `StateLedgerRestore.RestoreAsync` / `RestoreFromFileAsync`, their options and
  summary records, the format DTOs (`StateLedgerExportHeader` / `StateLedgerExportRecord` /
  `StateLedgerExportTrailer`), and `StateLedgerRestoreException`.
- **Where the fingerprint lives, and what "schema version" means.** The declaration fingerprint is
  `StatesmanManifest.Fingerprint` (SHA-256 of the canonical compact manifest JSON, computed once by
  `StatesmanDeclarationBuilder.Build`). **No store persists it** — nothing under
  `src/Statesman.Persistence.*` knows the fingerprint — so export and restore both take the
  `StatesmanManifest` as an explicit argument (the runtime exposes it as `IStatesman.Manifest`), and
  restore compares the export header's fingerprint against the manifest the operator supplies, not
  against anything the target store recorded. The "schema version" the sketch mentions is the
  **export format version** (`statesman.ledger-export/v1`, mirroring `StateFixture`'s
  `statesman.fixture/v1`), refused when unrecognized; per-record `SchemaVersion` is carried verbatim
  and *not* validated, because exact restore reproduces history as it was and the runtime's declared
  migrations upgrade old schema versions at read time exactly as they would for the original store.

**Refusal is total, never partial (case (b) as the sketch requires, plus two validation refusals):**
restore reads and validates the entire export — format, root, fingerprint, every record's
`StateRecord.Validate()`, and the trailer's record count (a truncated file has no trailer or a count
mismatch) — before contacting the target at all; then checks `IStateLedgerReplica`
(`NotSupportedException` if missing); then, by default, refuses a target whose `IPartitionCatalog`
already lists any partition under the export's root, because `GlobalPosition` values from
independent histories collide (EF Core's unique index on `GlobalPosition` would fail *mid-import*,
the exact partial-import outcome the sketch forbids; other providers would silently interleave).
`AllowNonEmptyTarget` opts out for the two legitimate cases: re-running a restore after a
store-side failure mid-import (every `ImportAsync` is exact and idempotent, so re-running is the
recovery path) and restoring over a store known to share the export's position lineage. Format is
newline-delimited JSON — one header line, one line per record, one trailer line — so both directions
stream and the header is checkable before a single record is parsed.

**Found and fixed during Phase 6 execution (2026-09-04, commit `cafdfbe`):** the planning refinement
above said Tiered "deliberately does not implement `IStateLedgerReplica`", and that was true of the
class's interface list — but `TryGetCapability<IStateLedgerReplica>` on a Tiered store still
*succeeded*, because `TieredStateLedgerStore.TryGetCapability(Type, out object?)` forwards every
capability hot-first and the Tiered constructor requires the hot store to implement
`IStateLedgerReplica`. Task 4's cross-provider test (restore into a Tiered store must throw
`NotSupportedException` pointing at cold) caught it: restore silently imported every record into the
hot cache and the cold authority never saw them. The fix is a veto inside the generic forwarder —
`IStateLedgerReplica` is never forwarded through a Tiered store, with a regression test in
`TieredCapabilityForwardingTests` and a clause in `docs/architecture/capabilities.md`. The rejected
alternative was forwarding it to *cold* (so restore-into-Tiered would mean restore-into-cold): under
`PreferHot` a stale hot head would then be served after the restore, so forcing operators to target
the cold store is the safer contract. This is the first concrete data point on the long-deferred
Tiered forwarding-policy question: generic hot-first forwarding is wrong for any capability whose
semantics are "authoritative write", and the plan's pre-flight scan should have checked the
forwarder, not just the interface list, when it assumed a capability was absent.

**Found by the Phase 6 final whole-branch review and fixed in the fix wave (2026-09-04):** the Redis
bullet above claimed the Lua max-advance made position reuse impossible. It did not, and worse, the
change feed could silently lose records: Redis sorted-set scores are IEEE doubles (exact only for
integers up to 2^53), the Redis change feed scores its members by `GlobalPosition`, and the
filesystem provider allocates positions from UTC ticks (about 6.4e17). So a filesystem export
restored into Redis — a documented, default-options path — had adjacent positions rounding to the
same score, the exact-replace import's remove-by-score deleting the neighbouring record, and the
Lua `tonumber` comparison failing to advance the counter. The reviewer reproduced both against a
live Redis; the planning-time verification checked that the script ran inside/outside `MULTI` but
never asked whether its *arithmetic* was exact. The fix: `RedisStateLedgerStore.ImportAsync` refuses
any position above `MaxImportablePosition` (2^52 — half the exact range, so the appends that follow
a restore stay exact for another 2^52 positions) with `NotSupportedException` before touching any
key, the Lua script compares canonical decimal strings instead of doubles, and the docs state the
bound: a filesystem export cannot be restored into Redis (restore it into in-memory, filesystem, or
EF Core). Reshaping the feed to an exact large-position representation (a lexicographic sorted set
keyed by zero-padded position, say) would lift the bound and is a candidate follow-on, not Phase 6
scope. The same review also tightened restore (a record line whose `root` differs from the header's
root is now refused — the fingerprint check alone did not cover hand-merged files), made
`ExportToFileAsync` write to a sibling temporary file and move it into place only on success (a
failed export previously destroyed the previous backup at that path), and corrected the guide's
description of the non-empty-target hazard (in-memory/filesystem interleave, EF Core fails on its
unique index, Redis *overwrites* the colliding entry). Generalization worth carrying into Phase 7's
planning: when a plan adopts a provider primitive (a Lua script, a sorted-set score, a column type),
the pre-flight scan must state that primitive's value domain and confirm the data fits it — two of
this phase's three real defects (this one and the Tiered forwarder) came from checking the wrong
layer.

### Phase 7 — Outbox bridges

Adapter package(s) (e.g. `Statesman.Outbox.*`) consuming `IStateChangeFeed` with a persisted
cursor, delivering at-least-once to a message broker. Strictly a consumer of the durable feed from
Phase 2 — introduces no new core concept and keeps observation (`StateChangeHub`) distinct from
delivery, per ADR 0004. Must land after Phase 2.

#### Design (2026-09-05)

**Two packages.** `Statesman.Outbox` carries the contracts, the dispatcher, the in-memory and
filesystem cursor stores, the recording in-memory sink, the hosted worker, and the DI extension;
its contract and dispatcher types use only `Statesman.Abstractions`, while the worker and the DI
extension reference `Statesman.Extensions.Hosting`. `Statesman.Outbox.Redis` carries the Redis
Streams sink and the Redis cursor store on the already-pinned `StackExchange.Redis` 3.1.31. Zero
new third-party dependencies. Neither package adds an `IStateCapability` to
`Statesman.Abstractions` nor a public `IStateLedgerStore` implementation to a provider assembly, so
`docs/architecture/capabilities.md` and `CapabilityMatrixTests` are untouched — a deliberate
consequence of keeping `IOutboxCursorStore` out of the capability system.

**Contracts.**

```csharp
public interface IStateChangeSink : IAsyncDisposable
{
    string Name { get; }
    ValueTask PublishAsync(IReadOnlyList<StateChangeMessage> batch, CancellationToken cancellationToken = default);
}

public interface IOutboxCursorStore
{
    ValueTask<StateChangeCursor?> ReadAsync(string outboxId, CancellationToken cancellationToken = default);
    ValueTask WriteAsync(string outboxId, StateChangeCursor cursor, CancellationToken cancellationToken = default);
}
```

The sink is a batch contract, never single-record: a single-record signature forces a round trip per
record and forbids pipelining, and a batch signature can always be implemented one at a time. The
cursor advances once per accepted batch.

**Message shape.** `StateChangeMessage` is a flattened, wire-versioned DTO carrying `Format`
(`statesman.state-change/v1`), `MessageId`, `Store`, `Root`, `Path`, `Partition`, `Address`,
`Revision`, `GlobalPosition`, `OccurredAt`, `Operation`, `Status`, `ValueType`, `SchemaVersion`,
`Source`, `Fingerprint`, `ContentType`, `Payload`, `CorrelationId`, `CausationId`, `Metadata`, and
`Error`. It is deliberately *not* `StateLedgerExportRecord`: reusing that would make
`Statesman.Outbox` depend on `Statesman.Tooling`, and `statesman.ledger-export/v1` is a file format
that must be free to version for file-shape reasons a wire contract does not share. The repo
already flattens `StateRecord` independently in three providers, so a fourth is the established
shape rather than a new duplication.

`MessageId` is `"{Store}/{Address.Canonical}#{Revision}"` — the semantic dedup key, unique by
construction on every provider (per-address exclusion guarantees one record per
address-plus-revision) and stable across an export/restore. `GlobalPosition` is the *transport*
dedup key: unique within one store's position lineage, meaningless across stores, which is why
`Store` is a first-class field. The payload is carried as opaque bytes with a `ContentType` supplied
from options (default `application/json`) and is never deserialized, matching restore's rule that
declared schema migrations still apply at read time. `Fingerprint` is supplied from options because
no store persists `StatesmanManifest.Fingerprint`; it is nullable so an outbox over a bare store
still runs. `FreshUntil` and `ServeUntil` are deliberately excluded: they are cache-policy fields
meaningful only to the runtime that wrote them, and a public wire contract should not leak cache
policy to broker consumers.

**Cursor-store semantics.** `ReadAsync` returns `null` — never `new StateChangeCursor(0)`, which
throws — before the first write. `WriteAsync` is **monotonic**: a write at or below the stored value
is a no-op. Monotonicity is what stops a split-brain double-writer from rewinding the cursor and
mass-re-delivering, and, more importantly, from jumping it forward past records the other worker had
not yet published. Storing the cursor inside the ledger under a reserved address is rejected: every
provider writes the change-feed structure inside `AppendAsync`, so a cursor write re-enters the feed,
advances the cursor, and writes again — unbounded self-feeding write amplification at the poll rate,
not a filterable nuisance.

**Lease gating.** `OutboxOptions.RequireLease` defaults to `true`. A store without
`IStateLeaseProvider` then throws `NotSupportedException` naming the capability — signaling case (b).
Setting it to `false` runs unleased and records the degradation on the dispatcher, with the hosting
layer logging a defined event once — signaling case (a). Case (a) alone would be wrong as a default
here: two unleased workers on one store do not merely double-publish (which at-least-once tolerates)
— they race the cursor store, and a last-writer-wins cursor write can move the cursor past records
the other worker never published, a silent loss at-least-once must not permit. The lease id is
`"{root}:{storeName}:outbox:{outboxId}"`, mirroring `StatesmanRuntime`'s
`"{Id}:{storeName}:maintenance"` shape so two outboxes over one store do not exclude each other.

**Worker loop.** Acquire the lease, read the cursor, read the feed from it, publish in batches of at
most `BatchSize`, persist the cursor after each accepted batch, renew the lease at `LeaseTtl / 3`
while dispatching, and stop before the next batch when `RenewAsync` returns `false` without
advancing the cursor. Publish-then-persist is the required ordering for at-least-once: a crash
between the two re-delivers rather than loses. This makes the outbox worker the **first production
caller of `IStateLease.RenewAsync`**, closing a Phase 1 parked item. A permanently rejected record
blocks the cursor by default — bounded exponential backoff, the failure surfaced as
`LastDispatchError` and logged, and an explicit opt-in `SkipPoisonAfterAttempts` (default `null`,
never skip) for operators who choose otherwise. Silently skipping is precisely the "falls back to
weaker semantics" failure the ROADMAP 0.3 exit criterion forbids.

**Redis Streams entry ids.** The sink publishes each message with the explicit `XADD` id
`"{GlobalPosition}-0"`. A live probe against `redis:7-alpine` (Redis 7.4.11) through
StackExchange.Redis 3.1.31 confirmed that an id at or below the stream's top entry is rejected as a
`RedisServerException` whose message is `ERR The ID specified in XADD is equal or smaller than the
target stream top item`, and that ids of the magnitude of filesystem UTC-tick positions (6.38e17)
are accepted exactly. Explicit ids therefore give server-side dedup for free: a re-publish after a
crash is rejected rather than duplicated, and the sink treats that specific rejection as a benign
duplicate. The 2^52 `RedisStateLedgerStore.MaxImportablePosition` bound does **not** apply — stream
ids are two unsigned 64-bit integers, not sorted-set scores. `StreamIdempotentId` /
`StreamAddOptions` are deliberately not used: they require a Redis 8.2+ server and CI runs
`redis:7-alpine`.

**What "delivered" honestly means.** The outbox promises exactly this:

> Every record this outbox reads from the feed is handed to the sink at least once, and the
> persisted cursor never advances past a record the sink has not accepted.

Composed with the feed, that is at-least-once delivery *of every record the feed yields* — and the
feed is documented to be able to (a) permanently skip a record whose position was allocated before,
but committed after, a later record the outbox already consumed, and (b) omit records pruned before
the outbox reached them, which on Entity Framework Core with any non-default retention can happen
milliseconds after the write because `StateHandle` prunes after every successful append. The outbox
therefore **cannot** claim "every committed state change is delivered". One configuration is
genuinely complete and is named as such in the guide, in `docs/providers/index.md`, and in the XML
doc on the dispatcher: **Entity Framework Core as the feed source with
`StateRetentionPolicy.KeepAll`**, where position and record commit in one serializable transaction
and nothing is pruned. Upgrading that promise for the other providers requires the feed-hardening
work of the post-Phase-2 addendum — moving position allocation to commit time, or per-provider
in-flight-position tracking, neither of which exists today — and that is the **named prerequisite**
for ever restating the guarantee, not a Phase 7 task.

**Superseded by Phase 8 (2026-09-07).** The named prerequisite shipped. The feed is lossless within
retention on every provider, so the complete configuration widens from Entity Framework Core with
`StateRetentionPolicy.KeepAll` to any provider with `KeepAll`, with the filesystem crash window as
the one residual. The paragraph above is the Phase 7 record; `docs/guides/outbox.md` and
`StateChangeDispatcher`'s XML doc carry the current wording.

Over a tiered store both capabilities resolve correctly under the forwarding policy above: the feed
delegates to cold (the authority, and the position lineage the cursor lives in) and the lease
resolves hot-first (where the workers are). Key the cursor by the *tiered* store's `Name`, not
cold's, so swapping the hot tier does not orphan it — and note that pointing one outbox at a tiered
store and another at its cold store directly yields two independent cursors over the same records.

#### Refined during Phase 7 planning (2026-09-05)

Decisions taken before implementation, recorded here rather than left to the implementer.

- **`RequireLease` defaults to `true`.** An outbox over the filesystem or in-memory provider does
  not run without an explicit `RequireLease = false`. Chosen over the friendlier default because the
  ROADMAP 0.3 exit criterion is "no distributed method silently falls back to process-local
  semantics", and the unleased failure mode here is silent loss, not tolerable duplication.
- **Entity Framework Core cursor storage is deferred.** Adding a `DbSet` to
  `StatesmanLedgerDbContext` forces a migration on every existing consumer — the same friction the
  `StatesmanLeases` table caused one phase ago, which the CHANGELOG still warns about. An
  EF-Core-backed deployment uses the filesystem or Redis cursor store, or supplies its own
  `IOutboxCursorStore`. A separate opt-in `Statesman.Outbox.EntityFrameworkCore` context is the
  follow-on if demand appears.
- **Two packages, not one.** Matching how the persistence providers split. A single package would
  make `StackExchange.Redis` a hard dependency of every outbox consumer.
- **No `StartAt` option in v1.** The feed has no paging or batch limit, so a first run against a
  large existing store pulls the whole backlog into memory in one `ReadAsync` call on Redis and
  in-memory. `BatchSize` bounds what is *published* per batch, not what the feed materializes. The
  full-backlog-on-first-run behaviour is documented rather than papered over with a
  start-from-head option that would silently skip history.
- **`FreshUntil` and `ServeUntil` stay off the wire.** A choice, not an oversight; recorded so it is
  not "fixed" later by someone who reads the omission as a gap.
- **No HTTP webhook sink in v1.** `Microsoft.Extensions.Http` is already pinned, so it would cost no
  new dependency, but a webhook sink needs retry, timeout, idempotency-header, response-code, and
  auth policy — real surface area, and `ROADMAP.md`'s line is specifically about message brokers.
  Named as the obvious second bridge.
- **The `tests/Statesman.Tooling.Tests` CI gap is closed in this phase.** The `redis-tests` job runs
  only `tests/Statesman.Redis.Tests`, so Phase 6's cross-provider round trips have never run against
  a live Redis. Phase 7 adds both `tests/Statesman.Outbox.Redis.Tests` and
  `tests/Statesman.Tooling.Tests` to that job — a one-line change bundled with the new Redis test
  project rather than filed separately.
- **The dispatcher's single-cycle method is public.** The repo bans `[InternalsVisibleTo]`, so
  `DispatchOnceAsync` must be public for tests to drive one deterministic cycle without a
  `BackgroundService` and a real timer. This is the single most important testability decision in
  the design.
- **The repo's existing plain-`ILogger` style is kept.** There are zero `LoggerMessage`
  source-generated methods and zero `EventId` constants in `src/` today; introducing the first ones
  here would be an unrelated change. Noted as an option, not taken.

### Phase 8 — Change-feed hardening (lossless feed)

`GlobalPosition` is allocated before the record is durably visible on the in-memory, filesystem, and
Redis providers, so a consumer that drains the feed while a lower position is still in flight
persists a cursor past a record it will never see. That is silent, permanent loss, and it is the
open design question the post-Phase-2 addendum parked (see that addendum, and the Phase 7 "Published
caveat" paragraph that inherits it).

**Ruling (2026-09-07): commit-time position allocation — option (A) — on the in-memory, filesystem,
and Redis providers.** Entity Framework Core already allocates at commit time and gains only a
regression guard. Tiered inherits its cold tier's guarantee and changes not at all. The two
alternatives — (B) an in-flight low-water mark and (C) a settle window — are recorded below as
rejected, with the reason each one dies, so neither returns as a later "improvement".

#### The guarantee the feed makes afterwards

This is the wording that ships on `IStateChangeFeed` in `src/Statesman.Abstractions/Ledger.cs`. It
is normative; the provider docs restate it, they do not extend it.

> **The guarantee.** Records are yielded in ascending position order, and no record is skipped: a
> consumer that resumes from the cursor of the last record it accepted eventually sees every record
> the store still retains at a higher position. A record may be yielded more than once across calls,
> so consumers must be idempotent — this feed is at-least-once, never at-most-once.
>
> A provider reaches that by allocating a record's position in the same step that makes the record
> visible here, so a position never becomes readable before a lower one exists. A write in flight
> therefore holds back the records committed after it, and the feed's tail can briefly lag the
> store's newest record. It lags; it does not skip.
>
> **What the guarantee does not cover.** Retention: pruning a stream can remove a record before a
> consumer reaches it, and the feed does not resurrect it — see each provider's documentation for
> which of its structures retention actually trims. A record imported through
> `IStateLedgerReplica.ImportAsync` at a position a consumer has already passed is not re-delivered
> to that consumer. And on the filesystem provider a crash between the record write and the
> change-log append leaves that record durably stored but permanently absent from the feed.

The operational restatement, which is what a test can assert on every provider at once: *a consumer
that drains the feed while another write is in flight, persists the cursor it got, and resumes from
it, still receives the in-flight record.* Note that this is strictly weaker than "the drain is
empty" — Redis satisfies the guarantee by allocating the in-flight writer a *higher* position rather
than by withholding anything, which is what commit-time allocation means when allocation happens
server-side.

#### Per-provider mechanism

- **In-memory (`InMemoryStateLedgerStore`).** A new `_feedLock` covers position allocation, the
  `StateRecord` construction, `stream.Records.Add`, and `_changes.Enqueue` as one critical section.
  `Interlocked.Increment` and the `AdvanceGlobalPosition` CAS loop both move under that lock, and
  `ImportAsync` enqueues and advances inside it — today it does them unlocked and in the opposite
  order. `ReadAsync` needs no change: every enqueue happens under the lock, so the queue is in strict
  position order and `ConcurrentQueue<T>` enumeration is a documented moment-in-time snapshot, which
  means a reader always sees a prefix of the published sequence.
- **Filesystem (`FileSystemStateLedgerStore`).** The existing global `_changeFeedGate` widens to
  cover `NextGlobalPosition()`, the record construction, the **history** file write, and the
  change-log append. The **head** file write moves outside the gate: `ReadAsync` re-reads records
  from the history file and never from the head file, and `ReadLatestUnsafeAsync` already prefers the
  newest history file over a stale head, so a head write lost to a crash self-heals. Both `AppendAsync` and `ImportAsync` acquire the gate and call `AppendChangeFeedEntryUnsafeAsync` directly — the gate-taking wrapper and the `WriteRecordUnsafeAsync` variant were removed as dead code, leaving only the `…UnsafeAsync` variant, which mirrors `ReadLatestUnsafeAsync`. Lock order stays *address gate → `_changeFeedGate`* in both writers; `ReadAsync` and
  `ListPartitionsAsync` take only `_changeFeedGate`; `PruneAsync` takes only the address gate. No
  cycle.
- **Redis (`RedisStateLedgerStore`).** `INCR` and all five writes fold into one Lua script, replacing
  the separate `StringIncrementAsync` round trip and the `MULTI`/`EXEC` with its `AddCondition`
  revision guard. The client does not know the position when it serializes the record, so
  `RedisRecord.GlobalPosition` is re-declared **last** in the DTO — the serialized JSON then always
  ends `,"globalPosition":0}`, the client sends everything but the trailing `0}` as a prefix, and
  Lua concatenates the position and the closing brace. `RedisPartitionEntry` already has
  `GlobalPosition` last positionally. Property order is irrelevant to `System.Text.Json`
  deserialization, so records written by earlier versions still read back: this is a serialization
  order change, not a storage-format migration. Inside the script the position reaches string form
  only through `string.format('%d', position)` — never `tostring`, never implicit concatenation of a
  number — and the script returns the position as a decimal string, parsed with `long.Parse`. No
  arithmetic happens in Lua: the new revision is computed client-side from the observed head and
  passed as a decimal string, the discipline `AdvanceGlobalPositionScript` already establishes.
  `ImportAsync` keeps its current shape (max-advance script, then the exact-replace transaction);
  with commit-time allocation its ordering becomes strictly correct rather than correct-with-a-window.
- **Entity Framework Core.** No production change. The position comes from the `StatesmanLedgerSequence`
  table row, whose `Value` is a concurrency token, inside the same serializable transaction as the
  record insert — so a would-be *N+1* writer must observe a **committed** *N* or its `UPDATE …
  WHERE Value = N-1` matches zero rows and EF Core raises `DbUpdateConcurrencyException`. That single
  row is a global serialization point, and it is what makes the feed safe here, not the transaction
  boundary by itself. **This is fragile in a specific way**: switching to a database `SEQUENCE`, an
  `IDENTITY` column, or `HiLo` would allocate outside transaction scope — which is precisely why
  those mechanisms exist — and would silently reintroduce tail loss. Phase 8 therefore adds a
  regression guard pinning the mechanism: the model has no database sequence, `GlobalPosition` is
  never store-generated, `StatesmanLedgerSequence.Value` is a concurrency token, and
  `StatesmanRecords.GlobalPosition` carries a unique index.
- **Tiered.** Unchanged. Its feed guarantee is exactly its cold tier's guarantee and the positions in
  its cursors are cold's positions, consistent with the "Forwarding policy" classification of
  `IStateChangeFeed` as an authoritative read implemented on Tiered and delegated to cold. Only the
  documentation changes.

#### Value domain of every primitive adopted (the Phase 6 discipline)

| Primitive | Domain / resolution | Consequence |
|---|---|---|
| Redis `INCR` reply | signed 64-bit integer, server-side | exact for any `long` |
| Lua number holding an `incr` result | IEEE double | exact only to 2^53 |
| Lua `tostring(n)` | `%.14g` in Lua 5.1 | **mangles integers above 10^14 — banned in this script** |
| Lua `string.format('%d', n)` | integer cast | exact to 2^53; the only formatter used |
| Redis sorted-set score | IEEE double | exact to 2^53; `MaxImportablePosition` (2^52) already bounds it and is unchanged |
| Append script reply | the position as a **decimal string**, parsed with `long.Parse` | avoids a second double round trip on the reply path |
| Filesystem `NextGlobalPosition` | UTC ticks, ~6.4e17 | far above 2^52 — a filesystem export still cannot be restored into Redis, exactly as `MaxImportablePosition`'s doc comment says |
| In-memory / EF Core positions | dense `long` from 1 | no bound issues |
| `StateChangeCursor(long)` | throws when `position <= 0` | "no cursor yet" is `null`, never position 0 — unchanged |

#### What Phase 8 does *not* fix

Prune loss is untouched — the fix neither helps nor hurts it — and after Phase 8 it is the only
remaining feed caveat besides the filesystem crash gap. The current documentation lumps four
different behaviours into one paragraph and gets two of them wrong; the corrected breakdown:

| Provider | What prune does to the feed | Prune loss? |
|---|---|---|
| Redis | `PruneAsync` touches only the per-address history sorted set, never the changes set | **No.** The feed retains everything and grows without bound |
| In-memory | `PruneAsync` rewrites `stream.Records`, never `_changes` | **No.** Same unbounded growth — a real regression against `MaxRevisions`/`MaxBytes`, which existed to bound memory |
| Filesystem | Prune deletes history files; the log line survives and `ReadAsync` skips past it | **Yes** |
| EF Core | `PruneAsync` removes rows from `StatesmanRecords`, the same table `ReadAsync` queries | **Yes** |

Also not fixed, and documented rather than glossed:

- **The filesystem crash gap.** A crash or I/O failure between the history-file fsync and the
  change-log append still leaves a durably-stored record permanently absent from the feed. That is a
  durability property, not a concurrency property, and no option here closes it. Appending the log
  line *first* and having `ReadAsync` stop at the first unreadable record was considered and
  rejected: a crash between the log line and the record write — or an ordinary `PruneAsync` — would
  then wedge the feed permanently at that position, and the repair tooling that would fix it
  (ROADMAP 0.2's still-unbuilt filesystem recovery and compaction tooling) does not exist. Under the
  chosen ordering a dangling log line can only mean "pruned", so skipping it stays correct.
- **Import below a consumer's watermark.** A restore replayed into a live store can land a record at
  a position a consumer has already passed. That is inherent to restoring into a live store, is not
  new, and is stated in the doc comment rather than implied to be fixed.
- **EF Core cross-address contention surfaces as an exception, not a retry.** All EF Core appends
  already serialize on the sequence row across every address, and the `catch (DbUpdateException)`
  path rethrows when a *different* address's write condition still matches. On SQLite this never
  manifests, because `IsolationLevel.Serializable` opens as `BEGIN IMMEDIATE` and writers queue on a
  database-wide write lock. On SQL Server or PostgreSQL a concurrent cross-address append can
  surface `DbUpdateConcurrencyException` to the caller. Pre-existing, out of scope for Phase 8, and
  to be recorded as a finding if a Phase 8 concurrency test hits it — never "fixed" by weakening the
  test.

#### Rejected alternatives

**(B) In-flight low-water mark.** Track allocated-but-unpublished positions in a sorted set beside
the high-water counter and sample the ceiling once, atomically, *before* the read
(`ceiling = inFlight.Count == 0 ? highWater : inFlight.Min - 1`). It is exact, needs no format
change, and costs one lock per append with no serialization of the write path — genuinely the
cheapest correct mechanism for a single process. It dies on two of the three providers.
**Filesystem, decisively:** a read-only consumer process — an outbox dispatcher with
`RequireLease = false` running beside the writer, which nothing in the docs forbids — never appends,
so its in-flight set is empty and its high-water mark is zero. Its ceiling is zero and it yields
*nothing, ever*. Making it yield everything instead restores the original bug, and making the mark
durable means an extra write per append plus a stale-file-after-crash wedge. **Redis:** the tracker
would have to live in Redis, costing a round trip to reserve and another to release, and a crashed
client would leave a reservation that wedges the feed forever unless it carries a TTL — which is
option (C) wearing a different hat. Adopting (B) on in-memory alone would leave one contract with
two mechanisms and two failure vocabularies.

**(C) Settle window.** Yield only positions older than some interval. It is a probability, not a
property: the window would have to exceed the worst-case fsync, the worst-case network round trip
plus client GC pause, and — on Redis — inter-process clock skew, since the only timestamp available
is `OccurredAt`, written by whichever process made the write. It adds latency to every consumer on
every read, permanently, in exchange for a guarantee that is still not a guarantee. And it
introduces a tunable with a default, which is exactly the Phase 7 footgun recorded in
`docs/superpowers/HANDOVER.md`: tests that pinned an interval to zero masked a Critical lease-renewal
bug. **The chosen fix has no tunable at all. That is a deliberate property, not an accident, and
Phase 8 adds no timing, interval, or threshold option to any provider.**

#### The filesystem trade-off, stated and accepted

Every append in the store now serializes behind one `WriteThrough` fsync instead of running
per-address in parallel — roughly 0.1–10 ms of global serialization per append with the default
`FlushToDisk = true`, depending on storage. The structure is not new: every append already
serialized on `_changeFeedGate` for the duration of one non-fsync'd `File.AppendAllTextAsync`; the
critical section just gets about two orders of magnitude longer. Moving the head write outside the
gate keeps one fsync inside rather than two.

The reason to accept it: **the change-log file is the only channel this provider has to a reader in
another process.** Making the log line the commit point, appended in allocation order with the
record already durable, is what makes the feed lossless for a cross-process reader — and an
in-process watermark provably cannot do that, per (B) above. The provider's documented audience is
"desktop tools, agents, local-first applications, and development environments where one process owns
the directory"; cross-address write throughput is not one of its headline properties. A second
consequence follows and is documented on the providers page: after this change a `ListPartitionsAsync`
or `ReadAsync` scan blocks concurrent appends **outright**, not merely their change-feed writes.

#### Refined during Phase 8 planning (2026-09-07)

Decisions taken while writing the implementation plan, recorded here rather than left to the
implementer.

- **The load-bearing assertion is resume-completeness, not an empty drain.** "The drain is empty
  while a write is in flight" holds on in-memory, filesystem, and EF Core after the fix but **not on
  Redis**, where the paused writer has not contacted the server at all and the concurrent writer
  legitimately takes the lower position. The shared cross-provider assertion is therefore the
  operational restatement above: drain, keep the cursor, resume, and require the in-flight record to
  appear in one of the two batches. The stricter empty-drain assertion is kept as a
  provider-specific test only where it is true.
- **The test seam is a `TimeProvider` that blocks on its *N*th call**, not a new production API. Every
  affected provider reads the clock for `OccurredAt` between allocating the position and publishing
  the record, and object-initializer members are evaluated in source order, so the seam already
  exists: in-memory call 1, filesystem call 2 (`NextGlobalPosition` calls the clock first), Redis
  call 1, EF Core call 1 inside the open transaction. Every test must await a signal that the pause
  was actually entered and fail if it was not, so a future initializer reordering turns the test red
  rather than vacuous. The helper lives in the test projects, not in `Statesman.Testing` — the
  shipped testing package should not grow a concurrency gadget.
- **A `tests/Statesman.Conformance.Tests` project lands with this phase.** Phase 1 deferred a shared
  conformance suite "to when a third provider exists"; five do, and this is the first guarantee that
  must hold identically across all of them. It references the provider packages the way
  `Statesman.Capabilities.Tests` already does, and — because it contains Redis-gated tests — it needs
  the same per-project `dotnet test` invocation in CI's `redis-tests` job that commit `4ab07ad`
  established.
- **Tiered is not a conformance subclass.** Its `AppendAsync` imports into the hot replica after the
  cold append, which adds clock calls from a second store and makes a pause index meaningless. Its
  guarantee is cold's by construction and is covered wherever cold is covered.
- **The EF Core conformance subclass uses a file-backed SQLite database, not `Data Source=:memory:`.**
  The existing EF Core tests share one open `SqliteConnection` across every context, which cannot
  host two concurrent transactions; a file database gives each context its own connection, so the
  second writer blocks on `BEGIN IMMEDIATE` and then proceeds, which is the behaviour under test.
- **No capability is added or removed.** `docs/architecture/capabilities.md` and
  `CapabilityMatrixTests.cs` stay untouched; `IStateChangeFeed` remains "Yes" on all five providers.
  A task that finds itself editing either has introduced a capability by accident.

### Phase 9 — Provider-native change notifications (`IStateChangeNotifier`)

The last unshipped bullet of ROADMAP 0.3 (`ROADMAP.md:45`) and the half of Phase 2 that was deferred:
a provider-native push hint that a store's `IStateChangeFeed` has advanced, so a consumer does not
have to wait out a poll interval to learn about a write. Phase 8 is the prerequisite that unblocked
it — "authoritative" now names a property a test can assert (see the "Addendum (pre-Phase-8,
2026-09-07)" at the end of this file), so the hint can be defined as strictly less than delivery
without leaving the reader to guess what the difference buys.

```csharp
public interface IStateChangeNotifier : IStateCapability
{
    IAsyncEnumerable<StateChangeNotification> SubscribeAsync(CancellationToken cancellationToken = default);
}

public readonly record struct StateChangeNotification;
```

`IAsyncEnumerable<T>` is what every streaming capability in this codebase already returns
(`IStateChangeFeed.ReadAsync`, `IPartitionCatalog.ListPartitionsAsync`), it needs no new lifetime
concept — the enumerator's disposal *is* the unsubscribe — and both implementing providers produce
one naturally. The two alternatives were rejected: a callback registration returning
`IAsyncDisposable` inverts control and matches nothing on this library's public surface, and a
`ChannelReader<T>` would put `System.Threading.Channels` across the public boundary for the first
time and bake a buffering policy into the contract.

#### The contract

This is the wording that ships on `IStateChangeNotifier` in `src/Statesman.Abstractions/Ledger.cs`.
It restates the pre-Phase-8 addendum and is normative; the provider docs restate it, they do not
extend it.

> The feed is **lossless within retention**: a consumer that resumes from the cursor of the last
> record it accepted eventually sees every record the store still retains at a higher position.
> A notification is a **latency hint only** — it is a signal to poll the feed now. It carries no
> delivery guarantee and may arrive for a record the feed will not yet yield, because a lower
> position is still in flight. A consumer that polls on a notification and sees nothing must treat
> that as normal and poll again; it must never treat the notification's own payload as delivery, and
> it must never advance its cursor from one.

Two further properties are part of the contract rather than provider detail:

- **The payload is empty, permanently.** `StateChangeNotification` is a `readonly record struct` with
  no members. The addendum forbids three things a payload would invite — treating the notification as
  delivery, advancing a cursor from it, and assuming the referenced record is readable — and a
  `StateChangeCursor` on the notification is precisely the shape that produces
  `cursor = notification.Cursor`. A `StateAddress` is only marginally safer: it invites filtering,
  and a consumer that filters misses records, because the feed is global. The type's job is to carry
  the doc comment. A reflection test pins that it exposes no public instance members, so a later
  "convenience" addition fails a test rather than only contradicting a paragraph. Adding a nullable
  property later is source- and binary-compatible, so starting empty is the reversible choice.
- **The subscription is established when enumeration starts, not when `SubscribeAsync` is called.**
  Enumeration is lazy: a hint for an append that lands before the first `MoveNextAsync` may be
  missed. That is inside the contract — a missed hint costs latency, never a record — and it is
  stated in the doc comment and in the provider docs rather than worked around.

#### Per-provider mechanism

- **In-memory (`InMemoryStateLedgerStore`) — Yes.** A `ConcurrentDictionary<Guid, Channel<StateChangeNotification>>`
  of subscribers, each a **bounded capacity-1 channel with `BoundedChannelFullMode.DropWrite`**, the
  sibling of the mode `StateChangeHub` already uses. Publishing is `TryWrite` per subscriber and
  never blocks: when a subscriber's channel is full the new hint is discarded, which is what turns a
  burst of *N* appends into at most one extra consumer cycle. The publish happens **after
  `_feedLock` is released**, in both `AppendAsync` and `ImportAsync`, never inside it — the lock is
  held by a thread that also holds the per-address `stream.Gate`, so running subscriber code under it
  would invert lock order, and Phase 8's own final review moved work *out* of that lock for cost
  reasons (`HANDOVER.md`, Phase 8 entry). `ImportAsync` publishes only when the import genuinely
  introduces a new position, matching the feed enqueue. `DisposeAsync` completes every subscriber
  channel, so an `await foreach` over a disposed store ends rather than hanging. The ordering nuance
  this creates is admitted, not fixed: after the lock releases but before the hint is raised, a later
  record can be enqueued and hinted first. Both hints say "poll now"; the feed's order is unaffected.
- **Redis (`RedisStateLedgerStore`) — Yes.** `PUBLISH` to `{KeyPrefix}:{Name}:notifications`, issued
  **client-side after `AppendScript` returns** and after `ImportAsync`'s transaction commits — not
  inside the Lua script. Subscription is `ISubscriber.SubscribeAsync(channel)` yielding a
  `ChannelMessageQueue`, which is itself an `IAsyncEnumerable<ChannelMessage>`, torn down with
  `UnsubscribeAsync` when the enumerator is disposed. Publishing client-side rather than in the
  script is deliberate: the contract already tolerates a lost hint, so in-script publishing would
  only buy robustness against a failure mode the contract permits, while modifying the exact script
  Phase 8 hardened. It is also strictly more correct for the hint's ordering — the record is provably
  already on the change-feed sorted set when the publish is issued — and `CommandFlags.FireAndForget`
  costs one extra command on the wire with no awaited reply, so the Phase 8 append latency budget is
  untouched. Redis pub/sub is **at-most-once with no backlog**: everything published while a
  subscriber is disconnected is lost forever. That is exactly the hint contract, and it is why
  pub/sub is the right primitive here and Redis Streams would be the wrong one.
- **Filesystem (`FileSystemStateLedgerStore`) — No.** There is no reliable cross-process primitive.
  An in-process-only signal is trivial to write and dishonest to ship: the change-log file is the
  only channel this provider has to a reader in another process (see "The filesystem trade-off,
  stated and accepted" above), so a notifier that dies at the process boundary would make the matrix
  cell claim a guarantee that does not survive the provider's own documented deployment shape — the
  silent degraded implementation `docs/architecture/capabilities.md` forbids. `FileSystemWatcher` is
  the tempting middle and fails on documented behaviour rather than on principle: its notification
  buffer can overflow and lose track of changes, a single file operation can raise more than one
  event, and network directories cap the buffer and depend on platform support. It would add a third
  notification mechanism with a third failure vocabulary, plus a watcher lifetime and an `Error`
  handler, to the one provider whose append latency is already dominated by an fsync. Same precedent
  as `IStateLeaseProvider` (Phase 1) and `IDistributedCapture` (Phase 4). If a watcher is wanted
  later it belongs outside the capability system, where it need not claim a guarantee.
- **Entity Framework Core — No.** `Statesman.Persistence.EntityFrameworkCore` references only
  `Microsoft.EntityFrameworkCore` and `.Relational` and describes itself as provider-neutral. Every
  push mechanism that exists is engine-specific — PostgreSQL `LISTEN`/`NOTIFY`, SQL Server query
  notifications — and SQLite, the only engine any test here runs against, has none. Implementing one
  means either taking a database-provider dependency this package has deliberately avoided, or
  shipping a "Yes" cell that is a no-op on the tested engine. A polling notifier would be worse: a
  degraded implementation wearing a capability's name, when EF Core consumers already have the same
  mechanism under an honest name in `OutboxOptions.PollInterval`.
- **Tiered (`TieredStateLedgerStore`) — Yes, implemented directly, delegated to `_cold`.** See the
  classification below.

#### Value domain and failure semantics of every primitive adopted (the Phase 6 discipline)

| Primitive | Value domain / failure semantics | Consequence for this phase |
|---|---|---|
| Bounded `Channel<T>`, capacity 1, `BoundedChannelFullMode.DropWrite` | When the channel is full the **new** item is discarded and `TryWrite` still returns `true`; `false` means the writer is completed, never that a hint was dropped | A burst of *N* hints collapses to at most one pending hint per subscriber, and a publisher never blocks or observes backpressure |
| `ChannelReader.WaitToReadAsync` | Returns `false` once the channel is completed and drained | The outbox reads that as "this notifier is finished" and falls back to the timer permanently, rather than spinning |
| Redis `PUBLISH` / `SUBSCRIBE` | At-most-once. No backlog, no persistence; everything published while a subscriber is disconnected is lost forever | Precisely the hint contract. The feed, not the channel, is what makes a record recoverable |
| `CommandFlags.FireAndForget` | The command is written to the socket and no reply is awaited; a failure is invisible to the caller | One extra command per append, no added round trip. A lost hint is inside the contract |
| `RedisChannel`'s implicit conversion from `string` | `[Obsolete]` in StackExchange.Redis 3.1.31 → CS0618 → a **build error** under `TreatWarningsAsErrors` | Channels are built with `RedisChannel.Literal(...)`. The neighbouring `RedisKey` conversions are not obsolete, so the file's existing key helpers are no precedent |
| `ChannelMessageQueue` | `IAsyncEnumerable<ChannelMessage>` via `GetAsyncEnumerator(CancellationToken)`; not `IDisposable` — teardown is `UnsubscribeAsync` | A queue that is never unsubscribed holds a server-side subscription for the multiplexer's lifetime, which in a long-lived host is a real leak |
| `PeriodicTimer` | Supports exactly one outstanding `WaitForNextTickAsync`, whose `ValueTask` must be consumed | The outbox loop carries one pending tick across iterations instead of issuing a second wait when a hint wins the race |
| `ManualTimeProvider` | Does not override `CreateTimer`, so it does not drive `PeriodicTimer` (the Phase 7 finding) | Outbox tests use a real, deliberately long `PollInterval` plus a signal, never virtual time |
| `StateChangeNotification` | A `readonly record struct` with no members; `default` is its only value | There is nothing on it to mistake for a cursor or for delivery |

#### Forwarding-policy classification

**Authoritative read over ledger contents — implemented on Tiered, delegated to cold**, joining
`IStateChangeFeed`, `IPartitionCatalog` and `IDistributedCapture`.

A notification exists to say "poll the feed now", and `TieredStateLedgerStore.ReadAsync` delegates
straight to `_cold`'s feed. A hint sourced from the hot tier would therefore point at a feed the
consumer never reads. Worse, the hot tier is populated by `TryImportAsync` *after* the cold append,
so a hot-sourced hint would fire for a record whose cold position is the one the consumer's cursor is
measured against — a different position lineage entirely. `TieredStateLedgerStore` implements
`IStateChangeNotifier` directly, delegating to `_cold` and throwing `NotSupportedException` naming
the cold tier when cold cannot back it, exactly as `ReadAsync` does.

Implementing it directly is also what closes the trap: the generic forwarder in
`TieredStateLedgerStore.TryGetCapability` tries `_hot` **first**, so a Tiered store that merely
inherited the forwarder would hand a Redis hot tier's notifier to a consumer reading an Entity
Framework Core cold tier's feed. That is the exact shape of the `IStateLedgerReplica` bug the
forwarding policy was written to prevent, and the load-bearing test of this phase asserts a hot
notifier is never used when cold has one.

#### The outbox wake path

`StatesmanOutboxHostedService` waits on `PeriodicTimer.WaitForNextTickAsync` and nothing else, so
today a change waits out up to one `PollInterval`. Phase 9 replaces that single wait with a race
between the timer tick and a wake signal drained from a capacity-1 `DropWrite` channel, fed by a
background subscription to the store's `IStateChangeNotifier` when it has one.

Four properties fix the shape:

- **`PollInterval` remains the floor and the fallback.** A missed hint costs at most one interval of
  latency, which is why keeping the timer is the contract rather than belt-and-braces. A store with
  no notifier polls exactly as it does today — signaling convention (a), documented degradation.
- **No new option.** Subscribe when the capability is there, poll when it is not. Phase 8 shipped
  with no tunable deliberately, and Phase 7's Critical lease-renewal defect came from an interval
  whose default no test exercised. Adding `WakeOnNotification` would reintroduce that footgun to buy
  nothing.
- **Never two concurrent `DispatchOnceAsync` cycles.** The dispatcher's poison counter and renewal
  timestamp are unsynchronized instance state and its doc comment says so. A wake only makes the
  existing loop's next iteration happen sooner; it never starts a second one.
- **A standby worker falls back to the timer.** A cycle that returns `LeaseUnavailable` puts the
  worker in standby: it waits on the timer alone until a cycle returns some other outcome. A worker
  that cannot take the lease cannot publish, so waking it per notification would add a lease
  round trip per write to a worker that has nothing to do — making hotter the exact cost recorded as
  parked after Phase 7 (a standby worker polls every interval and does not log it). Falling back to
  the timer bounds the cost of a worker that *consistently* loses the lease, and it still takes over
  within one `PollInterval` of the leader stopping. It does **not** bound a deployment's lease
  traffic, and the sentence that shipped here first claimed it did: `DispatchOnceAsync` acquires the
  lease at the start of every cycle and releases it at the end, so there is no persistent leader,
  replicas alternate winning the race under sustained writes, and each one clears standby on the
  cycle it wins. Measured on two replicas over one live Redis store at default options, lease
  acquires across both in a five-second window: 9 quiet either way; 763 with a notifier against 10
  with it hidden at 1000 writes; 2300 (2282 on a repeat) against 11 at 3000 writes. Delivery was
  unaffected in every run — exactly the expected distinct positions, zero duplicates, never two
  concurrent cycles. Holding the lease across cycles, or flooring hint-driven cycles, is a follow-on.

The subscription's lifetime is the service's. `DisposeAsync` currently disposes only the sink; it
must also cancel and await the subscription, or a `ChannelMessageQueue` survives for the
multiplexer's lifetime.

Two shipped sentences assert the opposite of all this and are corrected in the same phase:
`StatesmanOutboxHostedService.cs:9` ("The change feed has no push notification, so the outbox polls")
and `OutboxOptions.cs:47` ("The feed is polled; there is no push").

#### Bundled: a length guard on the filesystem change-log line parser

`FileSystemStateLedgerStore.ReadAsync` splits each change-log line on tabs and indexes `fields[0]`
through `fields[4]` with no arity or numeric check, so a torn final line — reachable by a
cross-process reader, and recorded as parked after Phase 8 — throws `IndexOutOfRangeException` or
`FormatException` out of the feed. `ListPartitionsAsync` parses the same lines the same way and has
the same defect. Pre-existing since Phase 2, not a Phase 8 regression.

The ruling is a **positional** guard, not a blanket skip. A line whose field count is not five, or
whose position or revision fails `long.TryParse`, is skipped **only when it is the final line of the
log** — that is the only line a partially-completed append can produce, since every later line was
written after it finished. A malformed line anywhere else is corruption and throws
`InvalidDataException` naming the file and the line number. Skipping it silently would drop records
from a lossless feed to hide a real problem. Both call sites use one shared parser.

Skipping the final line is only safe for an **in-flight** tear — a cross-process reader observing a
non-atomic append in progress — where the line completes on its own and the next read sees all of
it. A tear that is already **durable**, which is what a crash mid-append leaves on disk, never
completes, and the guard alone would turn a loud pre-Phase-9 failure into a silent loss: the next
append would write straight onto the partial line, and the merged line is still last, so it would be
skipped too and one committed record would be missing from the feed with no error anywhere. The
write side therefore starts a fresh line whenever the log's last byte is not a newline. A durable
tear then costs an `InvalidDataException` naming the torn line on the next read after a subsequent
append — never a lost record, which stays committed and readable by address. Recovery is to truncate
the trailing partial line.

Phase 9 bundles this and nothing else: it is a handful of lines in a file the notifier work does not
otherwise touch, it needs no design decision, and it removes a crash from the exact code path a
hint-driven consumer now hits more often.

#### Explicitly out of scope

Each of these stays on the follow-on list, unchanged by this phase:

- **Wiring `StateChangeHub` / `IState<T>.ObserveAsync` to the notifier.** The Phase 2 sketch says the
  hub "may subscribe to" it. Doing so would change the semantics of the library's oldest public
  observation API, on a phase whose stated value is a latency optimisation for the outbox. The hub is
  fed by the runtime's own writes and never touches a store; that stays true.
- **Any new tunable option**, on the outbox or on a provider.
- **The `IStateChangeFeed` paging / batch parameter.** Breaking, touches all five providers plus
  Tiered's delegation and the conformance suite, and needs real work behind it (Redis and in-memory
  materialize the whole since-cursor result). It deserves its own phase and must not ride along with
  a new capability.
- **An Entity Framework Core outbox cursor store.** Additive and small; the cost is the migration and
  release-note choreography, unchanged since Phase 7, and nothing about it interacts with this phase.
- **The filesystem change-log fsync decision.** A tiny diff behind a real performance ruling that
  needs a before/after measurement, not an implementer's judgment.
- **Holding the outbox lease across cycles (or flooring hint-driven cycles).** Added after the final
  review measured what the standby rule does and does not bound (see the fourth property above).
  Changing the lease lifecycle changes who leads and for how long, which is a coordination decision
  of its own, not a documentation fix.

#### Refined during Phase 9 planning (2026-09-08)

  interface "needs no new lifetime concept — the enumerator's disposal *is* the unsubscribe", and
  describes `DisposeAsync` only for the in-memory provider. Both the Redis and the tiered store ship
  a store-level disposal `CancellationTokenSource`, cancelled at the top of `DisposeAsync` and
  linked into every live subscription, so disposing the **store** ends its subscriptions regardless
  of `RedisStateLedgerStoreOptions.OwnsConnection` or the tiered store's `ownsStores`. Without it
  the interface's "ends when … the store is disposed" promise held only when the store happened to
  own what it wrapped. The in-memory provider carries the same guarantee through a `Volatile`
  disposed flag, set before its channels complete and re-checked after a subscriber registers, so a
  `SubscribeAsync` racing disposal cannot hang.
- **The Redis hint path swallows two exception types.** `PublishChangeHint()` and the
  `UnsubscribeAsync` teardown catch `RedisException` and `ObjectDisposedException`. A committed
  append must never surface a notification-pipeline failure as a failed write, and a lost hint is
  inside the contract — it costs one `PollInterval` of latency and never a record.
- **The standby rule does not bound a deployment's lease traffic**, only the cost of a worker that
  consistently loses the lease. Measured and corrected in the fourth outbox property above.
- **The bundled filesystem guard needed a write-side half.** The read-side guard alone converted a
  crash-durable torn tail from a loud failure into a silent loss of one committed record; the append
  now starts a fresh line when the log does not end in a newline. Corrected in the "Bundled: a
  length guard" section above.

### Phase 10 — 0.3 close-out

The phase that closes the follow-on list rather than opening a capability. Every previous phase
ended by naming what it deliberately left undone, and by the end of Phase 9 that list had grown to
eleven items across five phases: a lease taken and released once per dispatch cycle, a change feed
with no bound on a read, no Entity Framework Core cursor store, a filesystem change log the
provider's own flush option does not cover, no lease conformance suite, and a handover document
carrying two claims the code has contradicted since Phase 4. None of those is a new guarantee. Every
one of them is a promise the library already makes, kept only partly.

Two of them cannot wait. **The paging parameter is the last breaking change 0.3 left open**:
`IStateChangeFeed.ReadAsync` gains a required options argument, `main` is `0.4.0-alpha` with no 0.4
consumer in existence, and the window shuts the moment one appears. **The lease-renewal contract has
to be decided before a conformance suite can assert it**: the interface says only "returns `false` if
it was lost" and never defines "lost", and the two implementing providers already disagree — which is
exactly the disagreement a shared suite exists to expose, and the reason it cannot be written first.

Seven pieces of work, in dependency order. Nothing here is a new capability, so nothing here needs a
forwarding-policy classification; the "Forwarding policy (decided before Phase 7, 2026-09-05)"
classification list is unchanged by this phase, and `docs/architecture/capabilities.md` gains no row
and flips no cell. The one place Tiered's forwarder is touched is a comment (see "Verified
non-defects" below).

#### 1. What "lost" means on `IStateLease.RenewAsync`

`IStateLease.RenewAsync` returns `false` "if it was lost" and the word is undefined, so the two
providers implement two different contracts. Redis passes the TTL to the server
(`StringSetAsync(key, token, ttl, When.NotExists)`) and the key is gone once it lapses, so a renewal
after expiry returns `false` even when nobody else took the lease. Entity Framework Core checks only
that the row exists and its `Token` still matches, so it will happily extend a lease whose
`ExpiresAt` passed minutes ago — resurrecting a lease a successor was entitled to take.

**Redis's behaviour is canonical, and the contract now says so:**

> A lease is lost once its time-to-live has lapsed, or once another holder has acquired it.
> `RenewAsync` returns `false` in both cases. It never resurrects an expired lease, even when no
> other holder took it: a time-to-live that does not bound the hold is not a time-to-live, and a
> caller that could renew across expiry would hold a lease a successor has already been granted.

Choosing the other direction would have been the weaker guarantee. `AcquireAsync` already treats an
expired row as free — it hands the lease to a new caller without consulting the old holder — so an
EF Core lease that renews across expiry produces two live handles for one lease id, each convinced it
holds it. That is the failure mode the capability exists to prevent, and no amount of doc wording
makes it safe.

EF Core's `RenewAsync` therefore gains two things. First, an `ExpiresAt <= now` check evaluated
against the store's injected `TimeProvider`, the same clock `AcquireAsync` judges expiry by, so the
two halves of the provider agree about when a lease ended. Second, a `catch (DbUpdateConcurrencyException)`
around its `SaveChangesAsync` returning `false` rather than throwing. That second half is not
defensive padding: `StatesmanLedgerLease.ExpiresAt` is configured `IsConcurrencyToken()`, so a
concurrent re-acquisition that rewrote the row between this renewal's read and its save makes the
save's `WHERE` clause match zero rows and EF Core raises `DbUpdateConcurrencyException`. The lease
*was* lost, by precisely the definition above, and the contract says that is a `false`, not an
exception. The provider's `AcquireAsync` already treats the sibling `DbUpdateException` the same way
(`return null`, not throw) for the same reason, and `EntityFrameworkLease.DisposeAsync` already
swallows it on release.

Redis needs no code change. Its behaviour is the contract.

#### 2. The outbox holds its lease across cycles (persistent leader)

Phase 9's final review measured the cost of taking the lease once per dispatch cycle and recorded it
as this phase's headline Important: two replicas over one live Redis store at default options,
counting lease acquires across both in a five-second window, went from 11 with the notifier hidden to
2300 at 3000 writes. Lease traffic scaled with write volume, because a hint-driven cycle is a cycle,
and every cycle was an acquire-plus-release round trip.

**The model becomes a persistent leader.** `StateChangeDispatcher` holds `IStateLease? _lease` and
`long _leaseRenewedAt` across calls. `DispatchOnceAsync` begins by asking `EnsureLeaseAsync` whether
this dispatcher holds the lease *at the moment the cycle begins*: a held lease is renewed on
`OutboxOptions.LeaseRenewInterval` rather than re-acquired, and only a dispatcher that holds none
attempts an acquire. A refused renewal means the handle is worthless, so it is dropped and exactly
one acquire is attempted in the same cycle; a `null` acquire is `LeaseUnavailable` and engages standby
exactly as today. Lease traffic now scales with *time* — one renewal per `LeaseRenewInterval` per
leader — rather than with writes.

**No new option, and no new validation rule.** `LeaseRenewInterval` already exists and now governs
the cross-cycle renewal as well as the mid-drain one; its documentation changes from "while draining
the feed" to "while holding the lease". Renewal is checked once per cycle and a cycle runs at least
once per `PollInterval`, so worst-case renewal lateness is one `PollInterval` — one second against a
ten-second interval and a thirty-second TTL at the defaults. A deployment that configures
`PollInterval >= LeaseTtl` degenerates to today's per-cycle acquire rather than being rejected, and
the documentation says so instead of a validator refusing a configuration that still works.

**The subtle bug this phase must not ship** is the renewal clock. `DrainAsync` seeds
`long renewedAt = Stopwatch.GetTimestamp()` today, which is correct only because the lease itself is
fresh every cycle. Under a persistent leader that line must read `_leaseRenewedAt`, and every path out
of `DrainAsync` must write the threaded value back. An implementation that keeps stamping a fresh
timestamp per cycle, and writes *that* back, re-stamps the clock every second at the default poll
interval, never satisfies the renewal interval, and silently drops the lease at `LeaseTtl` — a
correctness regression that no existing test observes and that a reader of the diff will not see.

**Release is now an obligation with an owner.** `StateChangeDispatcher` becomes `IAsyncDisposable`,
gains a public idempotent `ReleaseLeaseAsync()`, and its remarks extend the sentence that already
assigns sink ownership: the hosted service disposes both, and a caller driving `DispatchOnceAsync`
directly (which `StatesmanOutboxExtensions.CreateDispatcher` exists to support) now owns the lease and
must dispose the dispatcher. `StatesmanOutboxHostedService` wraps its loop in
`try { … } finally { await _dispatcher.ReleaseLeaseAsync(); }` so all five exits release, and
`DisposeAsync` releases too in case `ExecuteAsync` never ran. `IStateLease.DisposeAsync()` takes no
cancellation token, so an already-cancelled stopping token cannot skip the release.

**The failed-cycle release stays where the invariant expects it.** In the catch that backs off after a
thrown cycle, the release happens **before** the delay. `OutboxOptions.MaxRetryDelay` is validated
below `LeaseTtl` with the message "so a stalled worker releases its lease rather than holding it while
doing nothing", and that sentence has to stay true. Releasing before the backoff keeps the
failing-worker handoff identical to today's, keeps the validation rule meaningful, and is the reason
this phase adds no option to govern it.

**What the standby and hint rules become.** The standby rule itself stays and is still needed: a
worker that cannot take the lease still cannot publish, so waking it per hint would still be one
acquire attempt per write. What becomes false by construction is the sentence Phase 9 shipped to
explain the measurement — "the lease is acquired and released once per dispatch cycle rather than held
across cycles: there is no persistent leader, so under sustained writes two replicas alternate winning
the race". Two replicas no longer alternate. One leads until it stops or dies, and takeover is
`PollInterval` after a graceful stop (which releases) or `LeaseTtl + PollInterval` after a crash
(which does not). Those two cases are stated separately in the guide, because only the first is
within one interval.

The new operational property is worth one sentence rather than an option: **one replica now does all
the work until it dies**, where replicas previously shared load by accident. For an outbox, one writer
is the entire point, so this is the intended shape — but it removes incidental load sharing that an
operator reading the old numbers might have been relying on.

#### 3. `StateChangeReadOptions` — a bound on a feed read (breaking)

`IStateChangeFeed.ReadAsync` takes a cursor and nothing else, so a first run against a store with
existing history pulls the whole backlog, and on Redis and the in-memory provider materializes all of
it before yielding the first record. `docs/providers/index.md` and `docs/guides/outbox.md` both
document that as a limitation. Phase 10 closes it.

**The shape follows the house pattern rather than inventing one.**
`IStateLedgerStore.ReadHistoryAsync(StateAddress, StateHistoryOptions, CancellationToken)` already
exists for exactly this job, so the feed gets its sibling:

```csharp
// src/Statesman.Abstractions/Policies.cs, beside StateHistoryOptions
public sealed record StateChangeReadOptions
{
    public static StateChangeReadOptions Default { get; } = new();

    public int? Take { get; init; }

    public void Validate();
}

// src/Statesman.Abstractions/Ledger.cs
IAsyncEnumerable<StateChangeEnvelope> ReadAsync(
    StateChangeCursor? from,
    StateChangeReadOptions options,
    CancellationToken cancellationToken = default);
```

An options record rather than an `int?` parameter, so a later `MaxBytes` or address filter is
additive; one vocabulary for "bounded read" across the two enumerating APIs; and a static `Default`
so the common "read to the tail" call site is a named constant rather than a fresh allocation or a
`null` with a second meaning.

**`Take` defaults to `null`, not to 100.** `StateHistoryOptions.Take` defaults to 100 and that default
is already a documented trap — the export tooling has to pass `Take = null` explicitly because the
default "would otherwise truncate long streams silently". On a resumable feed a default cap is worse
than silent truncation: it makes a fresh outbox with a large backlog look like it stalled. `null`
means "read to the tail", which is exactly today's behaviour, so the default is source-compatible in
meaning even though the signature is not.

**`Take` bounds records the provider *yields*, on every provider.** This is the rule, and it is
stricter than "bound what the provider parses" for a reason that is not cosmetic. The filesystem
provider's `ReadAsync` skips a dangling change-log entry whose history file retention already deleted.
If `Take` bounded parsed entries, a page consisting entirely of dangling entries would come back
empty while live records sat above it, the outbox's paging loop would read "empty page" as "caught
up", and the cursor would stall at that position forever. So the filesystem scan continues past a
dangling entry and stops only when `Take` records have actually been yielded or the log ends.

The rule forces one contract sentence into the `IStateChangeFeed` remarks:

> A page shorter than `Take` means the provider reached its tail as of that read; because a write in
> flight holds back later records, it does not prove the feed is exhausted.

That was already true before this parameter existed, for the in-flight-write reason the guarantee
paragraph states. The parameter makes it something a caller has to act on rather than merely know.

**Every provider honours it natively**, which is what makes the parameter legitimate under the rule
that a capability is implemented exactly or not at all: in-memory appends `.Take` to its LINQ chain;
EF Core appends `.Take` before enumerating, translated to server-side `LIMIT`/`TOP`, the same pattern
the file already uses for history; Redis moves to the `SortedSetRangeByScoreAsync` overload carrying
`skip`/`take`, emitting `ZRANGEBYSCORE … LIMIT 0 count`, with `take: -1` for "no limit"; Tiered
forwards the options unchanged. The filesystem provider is exact in yielded records but still reads
the whole log file into memory to find them — that is a storage property of an append-only text log,
not a silent process-local fallback, and it is documented as the provider's own limitation next to the
append-cost figure it belongs with.

**The outbox reads `BatchSize` per feed call and gains no option.** `StateChangeDispatcher` sets
`Take = _options.BatchSize` and loops pages until a page yields zero records, renewing between pages
through the `StillHeldAsync` check it already has. Two knobs collapse into one:
`OutboxOptions.BatchSize`'s documented caveat — "bounds what is published, not what the feed
materializes" — simply stops being true, and the client-side accumulator becomes the per-page buffer
rather than a second policy. The drain's termination condition changes from "the enumerator ended" to
"a page came back empty", which is the honest condition given the short-page sentence above. There is
deliberately no separate `FeedPageSize`.

**Breaking rather than additive.** An additive overload leaves the unbounded call as the path of least
resistance and re-creates the ambiguity the parameter exists to remove; and a defaulted parameter
cannot be inserted ahead of `CancellationToken` without breaking positional callers anyway, so
"additive" would really mean a second method on every provider. `main` is `0.4.0-alpha` and this is
the stated window.

#### 4. `Statesman.Outbox.EntityFrameworkCore` — the sixteenth package

Entity Framework Core is the one shipped provider with no outbox cursor store, and the recorded reason
was never that the store is hard: it is that "an existing Entity Framework Core consumer would need a
second migration this soon after `StatesmanLeases`". A separate `DbContext` answers that objection
instead of arguing with it.

**Its own context, deliberately.** `StatesmanOutboxCursorDbContext` holds one `DbSet` and one table,
and the package references `Statesman.Outbox` plus `Microsoft.EntityFrameworkCore` — never
`Statesman.Persistence.EntityFrameworkCore`, with which it shares no entity. `Statesman.Outbox.Redis`
is the precedent: outbox bindings live in their own satellite depending on the outbox plus the client
library. Bolting a `DbSet` onto `StatesmanLedgerDbContext` would force a migration on every existing
ledger consumer whether or not they want EF cursor storage; a separate opt-in context means only the
consumer who chooses it adds a migration, for one independent table. The design must not "simplify" by
merging the two contexts, because the separation *is* the feature.

**Monotonicity is one atomic statement.** `WriteAsync` issues
`Where(row => row.OutboxId == id && row.Position < cursor.Position).ExecuteUpdateAsync(…)`; a non-zero
row count is done. Zero rows means either the stored value is already at or above the cursor — the
correct no-op the contract requires — or the row does not exist yet, so the store inserts and retries
as the same conditional update if it loses the first-insert race to `DbUpdateException`. The
alternatives were each rejected for a specific reason: an optimistic concurrency token (what the
ledger's lease row uses) needs a read-modify-write round trip plus a retry loop, which is the right
tool when a write branches on other fields and overkill for one comparison; a serializable
`SELECT`-then-`UPDATE` transaction (what `AppendAsync` and `AcquireAsync` do) costs `BEGIN IMMEDIATE`
on SQLite on a write that happens every dispatch cycle. `ExecuteUpdate` with the predicate gives the
same monotonic-max semantics as the Redis Lua script: on SQL Server the row lock makes the predicate
and the assignment atomic, and on SQLite the statement serializes at table level, which is stronger.

**The gap is stated, not hidden.** There is no live-SQL-Server CI job the way `redis-tests` exists for
Redis, so the store ships with SQLite coverage and a documented limitation naming SQL Server
specifically. That is the same honesty rule the capability matrix applies to a provider that cannot
back a capability: an untested engine is recorded as untested.

#### 5. The filesystem change-log fsync

`FileSystemStateLedgerStoreOptions.FlushToDisk` defaults to `true` and the provider fsyncs its history
file and its head file. It does not fsync the change-log append — the very structure Phase 8 made the
commit point of the feed. So the provider's own durability lever promises durability it does not
deliver for the one write that decides whether a committed record is in the feed at all, and four
documents plus two XML doc blocks describe that as a caveat.

**The append honours `FlushToDisk`, and there is no second option.** A separate lever would split a
durability story the docs tell as one, and the `IStateChangeFeed` remarks already frame the gap as a
caveat *of* `FlushToDisk` rather than of something else. The append becomes an explicit `FileStream`
mirroring `AtomicWriteAsync`'s existing pattern: `FileOptions.WriteThrough` when flushing,
`FlushAsync`, then `Flush(flushToDisk: true)`.

**The cost is a gate on the change, not a footnote after it.** An append at `FlushToDisk = true`
performs two fsyncs today — history inside `_changeFeedGate`, head deliberately outside it — and this
adds a third. But the new one sits *inside* the gate, so the globally serialized portion goes from one
fsync to two, and the provider's documented ~1.9 ms/append of global serialization is the number that
doubles. **The implementer measures 200 appends at both option values, before and after the change, on
one machine, and records all four figures. If `FlushToDisk = true` append cost more than triples, the
work stops and reports the numbers rather than proceeding** — reversing to an opt-in second option is
then a decision with data behind it instead of an implementer's judgment.

**Honest about what a test can prove.** Whether a stream was opened `WriteThrough` and hard-flushed is
not observable from managed code, and the repository has no precedent to borrow: nothing in the test
suite proves `AtomicWriteAsync` fsyncs either — the only related test pins that `FlushToDisk` defaults
to `true`. Inventing a seam would mean either a new public surface existing only for a test or a
reflection assertion pinning a private method name, and the repository has zero
`[InternalsVisibleTo]` and keeps it. So the proof is a round-trip test at both option values plus the
measurement above, and the plan says plainly that the fsync itself is not black-box provable rather
than dressing a weaker test as one.

Closing this reduces `docs/guides/outbox.md`'s "two residuals" to one: only the lease residual on the
filesystem and in-memory providers remains.

#### 6. The lease conformance suite

`ChangeFeedConformanceTests` is the pattern — one abstract base per capability, a
`ConformanceStore` bundle, one subclass per provider, `Assert.SkipUnless` on the bundle being
`null` — and Phase 1 deferred a lease suite "to when a third provider exists". A third provider still
does not exist, and that is no longer the reason to wait: the two that do exist disagreed about
renew-after-expiry for nine phases, and a shared suite is what would have caught it.

`LeaseConformanceTests` joins the change-feed suite in `tests/Statesman.Conformance.Tests`, with
`IStateLeaseProvider? Leases` added to the existing `ConformanceStore` rather than a parallel bundle
type, so cleanup and disposal wiring is not duplicated. Subclasses: Redis under `STATESMAN_TEST_REDIS`,
and Entity Framework Core over SQLite. It asserts exclusive acquisition, `null` (never an exception)
on a held lease, renewal extending a held lease, `false` after release, `false` after expiry, and that
a stale holder's dispose does not release its successor's lease.

**Expiry is the one assertion that needs a per-provider seam**, and the suite says why rather than
weakening the assertion to fit both providers. EF Core judges expiry against its injected
`TimeProvider`, so a `ManualTimeProvider` fast-forward is exact. Redis's expiry is the Redis server's
own clock and ignores the store's `TimeProvider` entirely, so its only honest form is a genuinely
short TTL and a real delay. The suite exposes the TTL it acquires with and a hook that makes it lapse,
following the `PauseCallIndex` precedent the change-feed suite already sets for a provider-specific
constant a shared assertion needs.

**A conformance suite's break-the-mechanism proof is that it discriminates.** The exclusion assertion
is a reusable method, and a negative test runs it against a deliberately broken in-project lease
double whose acquire always succeeds, asserting that the assertion fails. A suite that cannot fail is
not a suite.

#### 7. Verified non-defects, and the handover corrections

Three items on the follow-on list turned out not to be work, and saying so is part of closing the
list.

- **Tiered's `IStateLedgerReplica` veto ordering.** Phase 9 recorded "move the veto above the new
  direct-implementation guard so the precedence is structural". `TieredStateLedgerStore` does not
  implement `IStateLedgerReplica` and is `sealed`, so `capabilityType.IsInstanceOfType(this)` is
  provably `false` whenever the type is `IStateLedgerReplica`: the two branches are mutually exclusive
  on the current type surface, no test can distinguish the two orders, and `sealed` rules out the
  test-only subclass that would create the distinguishing case. Reordering would be a change presented
  as a fix. The honest close is a comment at the self-check recording that it must stay below the veto
  should Tiered ever implement the capability, plus the existing behavioural test that already covers
  the veto.
- **Cross-process change-log append interleaving.** Real, and not fixable at the append layer. The
  fresh-line check and the append are two file opens under a process-local semaphore, so two processes
  can interleave; but a portable lock is a hand-rolled sidecar file (byte-range `FileStream.Lock` is
  unsupported on macOS, which CI runs, and `FileShare` is advisory on Unix), and it would close only
  the byte-interleaving symptom. What the feed contract actually depends on is a single cross-process
  `GlobalPosition` allocator, and the counter is an in-memory field seeded from wall-clock ticks.
  Building that is the feature "multi-process filesystem writers", which contradicts a constraint
  `docs/providers/index.md` states deliberately. Parked, with a comment at the fresh-line rule saying
  the check is process-local by design because the writer side is single-process.
- **The "broken relative links" in the Phase 6 and Phase 8 plan documents.** There are seven such
  links and none is broken: every one sits inside a fenced code block quoting prose destined for
  `docs/guides/` or `docs/providers/`, and resolves against its intended destination.
  `eng/validate.py` already walks `docs/superpowers` and strips fenced code, which is why it reports
  nothing. The handover sentence calling them broken is itself the error.

Two further handover claims are stale and corrected in the same pass: `IStateLease.RenewAsync` has had
a production caller since Phase 7 (`StateChangeDispatcher`), and EF Core's lease-acquire concurrency
race was fixed in Phase 4 with the catch/rollback/re-read shape plus two deterministic decision-logic
tests. Both are contradicted elsewhere in the same document, which is how they survived.

#### Explicitly parked, with reasons

Each of these was examined this phase and left undone on purpose.

- **Unbounded in-memory and Redis feed growth under `MaxRevisions`/`MaxBytes`.** A genuine defect and
  **the top Phase 11 candidate**: `PruneAsync` on both providers trims the per-address history and
  never the feed structure, so two options that exist specifically to bound memory do not bound it on
  two providers. The coherent fix is "feed retention follows stream retention", which would make all
  four providers uniform — but it changes the published feed semantics of the two providers that
  currently retain everything, turning "no prune loss" into "prune loss", and that is the user's
  decision rather than an implementer's. Size L.
- **Cross-process filesystem append locking.** See above: a cross-process position allocator is a
  feature, not a fix.
- **`MessageId` collision from ordinal `Root` versus canonical lower-casing.** The outbox's documented
  deduplication key can collide on Entity Framework Core, because `StateAddress` equality is ordinal
  on `Root` while `Canonical` lower-cases it. The fix is address-equality surgery across the library.
  A 0.4 design item.
- **The Entity Framework Core server-database cross-address append race.** Two concurrent cross-address
  appends can surface `DbUpdateConcurrencyException` on a real engine. Pre-existing, and structurally
  untestable while every EF Core test is SQLite, so it pairs with the SQL Server CI job that item 4's
  documented gap also wants.
- **An incremental filesystem change-log read.** Phase 10's paging made the outbox's page loop pay a
  full change-log scan per page rather than per cycle, quadratic in backlog size on the filesystem
  provider (see `docs/guides/outbox.md` and `docs/providers/index.md`). Carrying a byte offset
  alongside the cursor would make the read incremental and the page loop linear again, but that is a
  feature, not a fix: it interacts with the log's torn-tail rules and with the "`Take` bounds records
  yielded, not entries parsed" ruling above. A Phase 11 candidate beside the feed-growth item.

### Phase 11 — Feed retention, and the filesystem change-log index

The phase that takes the two items Phase 10 named and parked, because both are defects rather than
features and one of them is a regression Phase 10 itself introduced.

**The first is unbounded feed growth.** `PruneAsync` on the in-memory and Redis providers trims the
per-address history and never the feed structure, so `MaxRevisions` and `MaxBytes` — two options
whose entire purpose is to bound memory — do not bound it on two of five providers. Phase 10 left it
undone because the coherent fix changes those providers' published feed semantics, turning a
documented "no prune loss" into prune loss, and called that the user's decision rather than an
implementer's.

**The second is the filesystem page scan.** Phase 10's `StateChangeReadOptions` made the outbox's
drain a page loop, and on the filesystem provider each page re-reads and re-parses the whole
`_changes.log`. Draining a backlog of N records costs about N/`BatchSize` whole-log scans where it
used to cost one per cycle. The phase documented it as a known regression and parked the fix as a
Phase 11 candidate.

Neither can wait for a reason the other phases have already used. `main` is `0.4.0-alpha`, no 0.4
consumer exists, and Phase 10 already took a breaking change to this same interface in this same
window. The semantic change is also smaller than it sounds: `StateRetentionPolicy.KeepAll` is the
default with every bound null (`Policies.cs:89`), so a default-configured store loses nothing, and
the only deployment that observes a difference is one that explicitly configured a memory bound and
is currently not getting it.

Six pieces of work, in dependency order. Nothing here is a new capability, so nothing here needs a
forwarding-policy classification; the "Forwarding policy (decided before Phase 7, 2026-09-05)" list
is unchanged, `docs/architecture/capabilities.md` gains no row and flips no cell, and **Phase 11 adds
no public type, member, option or package** — both new types are private to the class that owns them.

#### 1. The uniform retention rule

The rule, and it is the same sentence in the interface remarks, in both guides and in the provider
documentation:

> A record leaves the change feed exactly when its history record leaves the store. Retention that
> removes a revision removes that revision's feed entry, on every provider.

Two of the five providers already satisfy it, and neither by anyone's decision. Entity Framework Core
has one table serving history and feed — `ReadAsync` queries `context.StatesmanRecords`
(`EntityFrameworkStateLedgerStore.cs:94-97`), the same `DbSet` `PruneAsync` calls `RemoveRange` on
(`:455`) — so its prune loss is a consequence of the schema, not a rule someone wrote. The filesystem
provider deletes the history file (`FileSystemStateLedgerStore.cs:253-336`) and never opens
`_changes.log` at all, so the record stops being yielded because `ReadAsync` cannot dereference its
line. There was no existing trim rule anywhere in the codebase to generalize; the rule had to be
written, and the honest form is the observable one those two already meet.

The two alternatives were rejected for reasons that are not preference. An opt-in
`TrimChangeFeed` knob would be **silently ignored on three of five providers** — Entity Framework
Core physically cannot keep a pruned record on a feed that is its history table, and the filesystem
provider physically cannot serve a record whose history file is gone — which is exactly what
`docs/architecture/capabilities.md`'s honesty rule and Phase 10's "implemented exactly or not at all"
ruling exist to prevent. A feed bound independent of stream retention (a store-level
`MaxFeedRecords`) invents a second retention vocabulary and would let the feed drop a record whose
history the store still holds: a *new* loss shape, strictly worse than the one being adopted.

**The test is written first, and its per-provider result is the proof.** One new test joins the
shared `ChangeFeedConformanceTests` base, which five subclasses already inherit (in-memory,
filesystem, Entity Framework Core, Redis, tiered). It appends three revisions to one address and two
to another, prunes the first address to `MaxRevisions = 1`, and asserts that exactly three records
survive on the feed, that the pruned address contributes exactly one, that the second address is
untouched (prune is per-address; the feed is cross-address), that positions are still strictly
ascending, that a cursor captured at a now-removed position still resumes at the next surviving
record, and that paging at `Take = 1` collects the same three with no gap, no duplicate and
termination on an empty page. Run before any production change, it must **fail on in-memory, tiered
and Redis and pass on filesystem and Entity Framework Core**. That discrimination is what proves the
test tests the rule rather than the suite, and it is recorded per provider rather than asserted in
prose.

The last clause is the break-the-mechanism half. `Take` bounds records *yielded*, not entries parsed,
and an implementation that removed feed entries without preserving that would return an early empty
page — which a paging consumer reads as "caught up" — and fail it.

**In-memory changes structure, not just a statement.** `_changes` is a `ConcurrentQueue<StateRecord>`
(`InMemoryStateLedgerStore.cs:10`) and a queue cannot be trimmed in the middle. It becomes an
`ImmutableSortedSet<FeedEntry>` ordered by position — `System.Collections.Immutable` ships in the
shared framework on every target, so the core package keeps its zero-dependency rule — where
`FeedEntry` is a private `readonly record struct (long Position, StateRecord? Record)` compared on
position alone. Every publication (an append, an import, a prune) builds a new set under `_feedLock`
and stores it in the field; a reader takes one volatile read of the field and works on a structure
nothing can mutate. That is what preserves the property today's read has, and it is the load-bearing
part of this change. Today's lock-free read is sound only because `ConcurrentQueue<T>` enumeration is
a moment-in-time snapshot of a position-ordered sequence, so a reader always sees a prefix of the
published sequence — and two in-memory tests pin exactly that
(`ReadAsync_yields_nothing_while_an_append_holds_the_feed_lock` and
`ReadAsync_never_skips_a_record_whose_append_was_in_flight_during_a_drain`) by pausing a writer
*inside* `_feedLock` and draining while it is paused; the first documents itself as "in-memory
specific, and stronger than the shared guarantee". An immutable set is the same kind of snapshot: any
root a reader sees was published whole, in position order, so it is a prefix, less whatever retention
removed. Two alternatives were rejected, one on paper and one by running it. A `ConcurrentDictionary`
keyed by position would keep the read lock-free and be wrong: its enumeration is not a snapshot, so a
reader could observe position P+1 (inserted after its enumerator passed P's bucket) without P, and a
paging consumer would advance its cursor past P forever — a lossless-within-retention violation
introduced by a change meant to bound memory. A mutable `SortedSet` read under `_feedLock` was the
plan's first design, and the Task 1 implementer proved it wrong by running it: the read became a wait
on the writer's critical section, and the two tests above — which hold a writer paused inside that
lock while they drain — deadlocked rather than failed. The immutable set costs a path copy per
publication (O(log N) allocations) and gives O(log N) insert and remove; a read seeks to the cursor
with `IndexOf` and walks the indexer for `Take` entries, O(`Take` · log N), with no lock at all.
`PruneAsync` publishes its removals as one new root, built under `_feedLock` inside the stream gate it
already holds — the `stream.Gate` → `_feedLock` order `AppendAsync` established (`:138`, `:158`) — so
a reader sees a whole trim or none of it and the two paths cannot deadlock. The `:12-18` comment is
rewritten rather than left: a stale comment on the most carefully-reasoned concurrency code in the
repository is worse than none.

**Redis trims both structures in one transaction.** The change-feed member and the history member are
the same bytes on every write path: the append script builds one Lua `record` string and `zadd`s it
to `KEYS[3]` and `KEYS[4]` (`RedisStateLedgerStore.cs:74-79`), and `ImportAsync` adds one
`serialized` value to both (`:318-321`). `PruneAsync` already materializes the exact `RedisValue[]`
it removes from history (`:407-413`), so the same array is exactly right for the feed. The removal is
**member-exact `ZREM`, never `ZREMRANGEBYSCORE`**: sorted-set scores are IEEE doubles, exact only to
2^53, which is the Phase 6 lesson `MaxImportablePosition` (`:84-93`) already encodes — a score range
is not a reliable identity for a position. The two calls move into one `ITransaction` so a concurrent
reader sees both removals or neither rather than a feed still serving a record the history no longer
holds. The two keys span hash slots, which makes prune standalone-only — the same documented shape
`ImportAsync` and `CaptureAsync` already have on this provider, so it adds no new Redis Cluster
constraint. The partitions hash is not touched: it holds one entry per address and is already
bounded, and removing an address's entry would delete it from `ListPartitionsAsync`.

What this deliberately does not do: it does not change any cursor semantics. `StateChangeCursor` is a
`long` compared with `>` (or `Exclude.Start` on Redis), never a lookup, so a cursor at a removed
position still resumes at the next surviving record — verified in all four readers
(`RedisStateLedgerStore.cs:496-498`, `InMemoryStateLedgerStore.cs:327`,
`EntityFrameworkStateLedgerStore.cs:96`, `FileSystemStateLedgerStore.cs:385`). It does not touch the
filesystem or Entity Framework Core providers' prune paths, which already satisfy the rule. And it
does not remove the filesystem provider's dangling change-log line: the record is gone from the feed,
but the log file still holds the line, so filesystem feed *storage* still grows with total writes.
That is compaction, and it is parked below.

#### 2. What the documentation had to stop saying

Four documents and two XML doc blocks currently assert the property the rule replaces, and one of
them was already wrong before this phase. `docs/providers/index.md:86` says "**Redis has no prune
loss** … grows without bound" and the same of the in-memory provider; `:173` says "on Redis and
in-memory the feed is not trimmed at all" and also calls filesystem and Entity Framework Core "the
two providers whose feed structures retention actually trims" — which was never true of the
filesystem provider, whose feed structure retention does not touch. `docs/guides/outbox.md:13` and
`:16` carry the same claim, `IStateChangeFeed`'s remarks (`Ledger.cs:330-332`) send the reader to
"each provider's documentation for which of its structures retention actually trims", and
`StateChangeDispatcher`'s remarks (`:22-24`) single out Entity Framework Core for prune-before-read.

All of them become one sentence, stated identically: retention costs delivered records on every
provider, and no provider trades that for unbounded feed growth any more. The `KeepAll` default and
the fact that the surviving qualifier is the one the docs already chose — "lossless **within
retention**" — are stated where an operator will read them. The import-residue note below gets its
one sentence in the restore section at the same time.

#### 3. A committed measurement harness, before the fix

The figures the filesystem page-scan regression is documented with — 2.3 / 18.5 / 83.7 ms per scan at
5,000 / 50,000 / 200,000 change-log lines — appear as prose in two documents and have **no committed
artifact behind them**. There is no `bench/` directory, no BenchmarkDotNet reference, and no test or
script that produces them. Phase 10's fsync task set the precedent that a performance claim is
measured before and after against a recorded baseline, and this phase has no baseline to measure
against.

So the harness lands before the fix, as its own commit: one test class in the filesystem test
project, every measurement gated on `STATESMAN_MEASURE_FEED_SCAN=1` and skipping otherwise, reporting
through `ITestOutputHelper` rather than asserting a wall-clock threshold that would flake on a shared
runner. It measures two things: a **scan at the tail**, writing N well-formed change-log lines
directly with no history files behind them so the figure is the log scan and nothing else, and
timing the first read separately from the median of the next ten — before the index those two numbers
are the same, and after it the second is the incremental cost the index exists to produce; and a
**backlog drain**, 20,000 real appends paged at `Take = 100` until an empty page, which is the shape
the regression actually harms. Figures published in the documentation are labelled as taken on the
development machine, not as a contract.

#### 4. The in-process change-log index

The fix is a memo **inside `FileSystemStateLedgerStore`**, not an offset carried alongside the cursor.
`StateChangeCursor` stays a bare `long`: every `IOutboxCursorStore` implementation persists one, so
adding a byte offset would break four cursor stores, one persisted JSON file format, one Redis value
shape and one Entity Framework Core column, and would push a store-specific field into a type
documented as portable across providers. It also could not help the case it most needs to — a cursor
read back after a restart would carry an offset from a previous process's view of the file.

The index is owned by the store instance and touched only under `_changeFeedGate`, which every reader
and this process's writer already hold. It remembers the offset one past the last complete,
well-formed line consumed; how many lines have been consumed, so a corruption report still names the
right 1-based line; the raw bytes of the last consumed line; the parsed
`(Position, Address, Revision)` entries in position order; and an intern table so N lines over K
addresses hold K address instances rather than N.

**The log is not position-ordered, and the index does not assume it is.** `ImportAsync` appends a line
carrying the imported record's own `GlobalPosition` (`:229-235`), which can be lower than positions
already in the log, and restoring into a non-empty target is a documented, supported scenario. The
memo therefore stores *entries* and inserts each one at its sorted place — an append lands at the end
because its position is the highest, an import binary-searches to its place — rather than assuming
file order is position order.

**Three invalidation rules.** A file shorter than the remembered offset means the file shrank:
truncated by the documented corruption recovery, replaced, or compacted by a tool that does not exist
yet — the index is discarded and the log fully re-parsed. This length check is a fast path rather than
the rule that carries correctness, though: it skips a doomed seek-and-read on a file already known to
be shorter than the remembered offset, but the tail-bytes rule below independently catches every
shrink anyway, this one included, because reading the remembered tail back at the remembered offset
hits EOF on any shorter file. The tail-bytes rule is the one that cannot be dropped: a same-length
rewrite defeats a length check entirely, so the remembered tail bytes are re-read at their remembered
offset and compared on every read; a mismatch discards the index too, and this is what actually
carries correctness for every shrink and every same-length rewrite. And an **unterminated final
fragment is never consumed**: it is parsed transiently for the current read — yielded if it parses,
which is today's behaviour for a complete-but-unterminated line, and skipped as a torn tail if it
does not — with the scanned offset left before it, so the next read re-parses it whole. Skipping the
tail re-verify would be a silent correctness hole, which is why it is stated as a rule rather than as
belt and braces.

Every existing behaviour of the read survives unchanged, and the plan enumerates them so a reviewer
can check rather than trust: a malformed final line is skipped, a malformed non-final line throws
`InvalidDataException` naming the correct 1-based line, a `\r\n` terminator is tolerated, `Take`
bounds records yielded rather than entries parsed, and a missing log file yields nothing rather than
throwing.

**The yield loop stops holding the gate for its whole duration.** Today the entire line scan happens
under `_changeFeedGate`, which blocks every append for the duration — so the quadratic cost is a
write-throughput problem, not only a read-latency one. The index is never enumerated outside the
gate, because a concurrent append mutates it; instead the read copies candidates in bounded chunks,
binary-searching to the first entry above the last position copied and taking at most 256 entries per
chunk, then dereferences and yields outside the gate. The gate is held for a chunk, not for a page.

**The tests are the expensive half, and four of them are mechanism proofs.** A shrink-invalidation
test that yields records whose lines are gone if the check is removed; a same-length rewrite that
must observe the new record rather than the remembered one; an out-of-order import after a warm read;
a torn tail after an incremental read, in both the in-flight shape (the fragment completes and yields
once) and the crash-durable shape (a fresh line after the tear, and the read throws naming the right
line); and a cross-process reader, two store instances over one directory, proving the suffix scan
works for a reader whose writer is another instance. Task 3's harness is then re-run with the gate
variable set and the before/after pair recorded.

What this deliberately does not do: it does not compact `_changes.log`, it does not make
`ListPartitionsAsync` incremental, it does not add cross-process append locking, and it does not make
the index survive a process restart. It is per store instance and per process, and a second process
pays its own first parse — which is the same single-writer premise
`AppendChangeFeedEntryUnsafeAsync`'s comment (`:664-670`) already states, neither strengthened nor
weakened.

#### 5. What the index documentation says instead

`docs/providers/index.md:99-103` and `docs/guides/outbox.md:168-173` currently tell an operator that a
filesystem-backed outbox draining a large backlog should raise `OutboxOptions.BatchSize`, and quote
the three unmeasured figures. Both are rewritten: the whole-log parse is paid once per store instance
and then per appended suffix, a paging drain is linear again, and the `BatchSize` advice is
**withdrawn** rather than softened. The new resident cost is stated rather than buried — an entry is
two `long`s plus a `StateAddress`, which is three string references, so about 40 bytes per
change-log line plus one shared set of strings per distinct address, roughly 8 MB at 200,000 lines,
held for the store's lifetime — along with what invalidates it and the fact that it is per process.
The three prose figures are replaced by Task 3's measured before/after pairs, labelled as taken on the
development machine by `STATESMAN_MEASURE_FEED_SCAN=1`. One further sentence has to go with them:
`docs/providers/index.md:133` currently says `ListPartitionsAsync`'s whole-log scan "is consistent
with the filesystem provider's `IStateChangeFeed.ReadAsync`, which has the identical cost and locking
shape", and that stops being true the moment the index lands — the catalog keeps the old cost and now
stands alone with it.

#### Explicitly parked, with reasons

Each of these was examined this phase and left undone on purpose.

- **The Entity Framework Core test-provider seam, with the SQL Server / PostgreSQL CI job and the
  cross-address append race it would make testable.** One deliverable, not two halves: the seam is 24
  hard-coded `.UseSqlite(` call sites across 9 test files with no shared fixture, and doing it without
  the job delivers local testability and no CI signal. Phase 12.
- **`_changes.log` compaction.** The actual fix for filesystem feed *storage* growth, which item 1
  does not address: prune leaves a dangling line per pruned record and nothing in the shipped code
  ever rewrites or truncates the log. `ROADMAP.md:32` already lists "filesystem recovery and
  compaction tooling" as unshipped. Item 4's index is designed to survive a future compactor — that is
  what its shrink check and tail re-verify are for — so the two can be designed apart without the
  second breaking the first. Phase 12.
- **Cross-process filesystem append locking.** Unchanged ruling from Phase 10: a portable lock is a
  hand-rolled sidecar file and would close only the byte-interleaving symptom while the in-memory
  `GlobalPosition` allocator the feed's guarantee depends on stayed single-process. Making
  multi-process writers work is a feature. Phase 12 at the earliest.
- **`MessageId` collision from ordinal `Root` versus canonical lower-casing.** Needs address-equality
  surgery across the library. A 0.4 design item.
- **`IsolationLevel.Snapshot` for `SnapshotDistributed` on Entity Framework Core.** The semantically
  closer mapping, and untestable without a server engine — so it pairs with the seam and its CI job
  rather than shipping on reasoning alone. Phase 12.
- **`ManualTimeProvider.CreateTimer`.** Genuinely open since Phase 7, small, and entirely orthogonal
  to both of this phase's themes. Phase 12.
- **Import residue at a changed position — newly documented, not fixed.** Re-importing an existing
  revision at a *different* `GlobalPosition` leaves residue on three providers: on Redis the old
  changes member survives with no history twin, because import replaces the history member by revision
  score and the changes member by position score; on the in-memory provider the old feed entry stays;
  on the filesystem provider the old log line now dereferences to the rewritten history file, so the
  record yields twice at two positions. A member-exact prune does not collect any of it. This is the
  "restore into a non-empty target from a different lineage" scenario `docs/providers/index.md:167`
  already calls colliding, it is pre-existing rather than created by this phase, and Phase 11's
  response is a code comment at each of the three import sites and one sentence in the providers doc.

## Addendum (post-Phase-2, 2026-09-03)

Phase 2's final whole-branch review found two Critical, cross-provider issues that no single
per-task review could see (each only looked at one provider). Both were real. One was fixed before
merge; the other is a genuine design gap, documented here rather than papered over, because the
still-unplanned `IStateChangeNotifier` half of this phase and any future outbox adapter (Phase 7)
depend on knowing exactly what guarantee this feed does and doesn't make.

**Fixed before merge, verified directly (not just claimed):** `TieredStateLedgerStore`'s default
`ReadMode` (`ValidateCold`) calls `ImportAsync` on the hot replica on every read that hits cold, and
`ImportAsync` was unconditionally appending to the change feed on InMemory and FileSystem — turning
ordinary reads through the default tiered configuration into an unbounded feed-growth leak.
Confirmed empirically, not just by reading the diff: temporarily reverting the `isNewPosition` guard
and re-running the regression test showed a triple `ImportAsync` of the same record producing three
change-feed entries instead of one. Both providers now only append when the import genuinely
introduces a new `GlobalPosition`, and both gained a regression test pinning this.

(The controlling session briefly and incorrectly concluded, mid-session, that this finding was a
"false positive": it lost track of an already-running fix-wave agent across a context-compaction
event, read that agent's uncommitted in-progress edit off the shared working-tree disk, and mistook
it for pre-existing history — then wrote that incorrect conclusion into the spec and dispatched a
second, different fix-wave agent for a narrower scope (a real `ReadAsync` file-sharing fix and a
real `CancellationToken.None` fix, both independently verified against the code and genuinely
needed — see below) without realizing the first agent was still active on the same file. Both
agents' edits were real, not fabricated, and turned out to be compatible; the second agent's edits
were deliberately reverted, not because they were wrong, but to let the first agent land its
already-further-along, independently-verified fix cleanly first — the second agent's fixes were
redone against that clean baseline afterward. Recorded here as a process note: losing track of
a long-running background agent across compaction, then re-deriving conclusions from a shared
working tree without checking who else might be mid-edit on it, produced a confidently-wrong
"already correct" claim — verify empirically and account for concurrent agents before writing a
correction into permanent documentation.)

**Not fixed, tracked as an open design question — resolve before building anything on top of this
feed:** `GlobalPosition` is allocated before the record is durably visible on four of five
providers (Redis: `INCR` then a transaction round-trip later; FileSystem: an in-memory counter then
two fsync'd writes later; InMemory: `Interlocked.Increment` then an enqueue moments later — only EF
Core allocates and commits the position inside the same transaction). A consumer reading while
position *N*'s append is still in flight but *N+1*'s has already landed sees only *N+1*, persists
that as its cursor, and can never see *N* — it will land below the consumer's watermark on the next
read. This is the standard change-data-capture "low water mark" problem, and as shipped, none of
`IStateChangeFeed`'s doc comment, the provider docs, or the tests say the feed can do this.

A real fix is either a stability window (only yield positions older than some settle interval, or
below the lowest currently-in-flight position — needs each provider to track in-flight allocations)
or moving position allocation to commit time everywhere (which EF Core already does, but doing the
same for Redis/FileSystem/InMemory means giving up the per-address write concurrency those
providers currently have — a real trade-off, not a small patch). Until one of these ships:
`IStateChangeFeed` consumers must treat the feed as **at-least-once with possible tail loss under
concurrent writes to different addresses**, not lossless — the spec's "push accelerates, feed is
authoritative" framing for `IStateChangeNotifier` (below) needs to be revisited against this before
that follow-on plan is written.

**Resolved in Phase 8 (2026-09-07).** Commit-time allocation shipped on every affected provider; see
the "Phase 8 — Change-feed hardening (lossless feed)" section above for the mechanism and the
"Addendum (pre-Phase-8, 2026-09-07)" below for the precise meaning "authoritative" now carries. The
paragraph above stands as the record of the gap, not as current behaviour.

**Also flagged by the same review, lower priority, tracked but not blocking:**
- **Retention/prune interaction is inconsistent and mostly undefined.** Pruning a stream deletes
  it from `ReadHistoryAsync` but each provider's change feed reacts differently: EF Core's feed
  silently loses the pruned records (it queries the same table `PruneAsync` deletes from);
  FileSystem's index file keeps a now-dangling line forever (silently skipped on read, never
  cleaned up); Redis's and InMemory's change-feed structures aren't trimmed at all and retain
  everything forever regardless of the store's own retention policy — for InMemory this is a real
  regression, since `MaxRevisions`/`MaxBytes` existed specifically to bound memory and the change
  feed now defeats that bound. Needs a decided, documented, and provider-consistent semantic (own
  follow-up).
- **`TieredStateLedgerStore` advertises `IStateChangeFeed` even in a hypothetical composition where
  its cold store couldn't back it** — `TryGetCapability<T>`'s direct-cast-first behavior means
  capability negotiation says yes unconditionally, and only a `NotSupportedException` on the first
  actual read would reveal a real gap. Not reachable with any of today's five providers (all
  implement the capability), but the same shape will recur for `IPartitionCatalog` (Phase 3) and
  needs an architectural answer then: either let `IStateCapabilityProvider` veto a direct cast, or
  have `TryGetCapability<T>` consult the provider before the cast when a store implements both.
- **No paging/batch limit on `IStateChangeFeed.ReadAsync`.** Only EF Core streams the underlying
  query; Redis and InMemory materialize the full since-cursor result before yielding. FileSystem
  already avoids the worse version of this — it sorts lightweight `(position, address, revision)`
  tuples first and re-reads each full record lazily inside the yield loop
  (`FileSystemStateLedgerStore.cs:294-338`), so it only holds the small tuples in memory, not full
  deserialized records — but it still reads the entire index file per call regardless of cursor. A
  consumer resuming after being offline a long time — the primary use case for a durable feed —
  pulls its entire backlog into memory in one call today. Worth deciding
  before any external consumer exists, since adding a batch parameter to a shipped capability
  interface later is a breaking change.
- `StateChangeCursor` carries no store identity, so a cursor obtained from one store can be passed
  to a different store's `ReadAsync` with no error, silently returning the wrong slice. Consider a
  store fingerprint if this proves to be a real footgun in practice.

**Genuinely fixed, empirically verified (commit `e37b4a7`):** `FileSystemStateLedgerStore.ReadAsync`
was not taking `_changeFeedGate` before reading the index file — the same gate
`AppendChangeFeedEntryAsync` already holds while writing to it — a real Windows file-sharing race
(broader than the Task 5 per-task review's "narrow Import-repair" framing: any concurrent read plus
any write). `ReadAsync` now acquires the gate around the file-exists check, read, and line-parsing
loop, releasing it before the second loop that does the actual yielding. A concurrent
`AppendAsync`/`ReadAsync` stress test reliably reproduced the exact pre-fix `IOException` (5/5 manual
runs against the unpatched code) and now passes consistently. `AppendAsync`/`ImportAsync` were also
passing the caller's `CancellationToken` into the change-feed append after the primary record write
had already durably committed — a cancellation in that narrow window made an already-successful
write look like it failed to the caller — both call sites now use `CancellationToken.None` for that
specific, already-committed-work append.

These caveats belong in `docs/providers/index.md`'s change-feed section (added as part of this
phase's final fix wave) so they're discoverable by users, not just by whoever reads this spec.
## Addendum (pre-Phase-8, 2026-09-07)

The open design question the post-Phase-2 addendum parked — `GlobalPosition` allocated before the
record is durably visible on four of five providers — is being resolved by the Phase 8 section
above, by commit-time allocation on every affected provider. The addendum's own text stays as
written; read it as history, and read Phase 8 for what ships.

The consequence for `IStateChangeNotifier`, which that addendum said needed revisiting first: the
spec's "push accelerates, feed is authoritative" framing now has a precise meaning, and it is this.

> The feed is **lossless within retention**: a consumer that resumes from the cursor of the last
> record it accepted eventually sees every record the store still retains at a higher position.
> A notification is a **latency hint only** — it is a signal to poll the feed now. It carries no
> delivery guarantee and may arrive for a record the feed will not yet yield, because a lower
> position is still in flight. A consumer that polls on a notification and sees nothing must treat
> that as normal and poll again; it must never treat the notification's own payload as delivery, and
> it must never advance its cursor from one.

That is compatible with ADR 0004 as written: notification is still not delivery, and the feed is
still what makes delivery durable. What changes is that "authoritative" is now a property a test can
assert rather than a word, so the `IStateChangeNotifier` follow-on plan is no longer blocked on
defining it.

## Addendum (pre-Phase-10, 2026-09-08)

Decisions taken while writing the Phase 10 section and its implementation plan. **As in Phases 8 and
9, they were taken without `AskUserQuestion` because the session ran under an autonomous `/goal`.**
Four are worth revisiting if that ruling was wrong, and each is listed with what reversing it would
cost.

1. **`RenewAsync` never resurrects an expired lease, even when nobody else took it.** Redis's
   behaviour became the contract and Entity Framework Core changed to match, rather than the reverse.
   The argument is that `AcquireAsync` already treats an expired row as free, so a lease that renews
   across expiry produces two live handles for one lease id. The cost of this ruling is that a slow
   holder whose renewal arrives one millisecond after its TTL loses a lease nobody was contending
   for, and must re-acquire — which the outbox's `EnsureLeaseAsync` now does automatically, so the
   cost lands on a direct `IStateLease` caller rather than on the shipped consumer. Reversing it means
   changing Redis, which would mean re-implementing expiry in a Lua script against the store's own
   clock instead of the server's; that is why this direction was chosen and not merely preferred.

2. **`IStateChangeFeed.ReadAsync` takes a required `StateChangeReadOptions` — a breaking change.** An
   additive second method was rejected because it leaves the unbounded read as the path of least
   resistance, and because a defaulted parameter cannot precede `CancellationToken` without breaking
   positional callers anyway. The window for this is `0.4.0-alpha` before a 0.4 consumer exists, and
   it closes on its own. If the ruling is wrong the cost is real: every external implementation of
   `IStateChangeFeed` and every external call site breaks at compile time, with no runtime surprise
   and no silent behaviour change, and thirty-five in-repo call sites move in one commit. The related
   sub-ruling worth naming separately is that **`Take` bounds records yielded rather than entries
   parsed**, which is what stops a filesystem page of nothing but pruned entries from reading as "the
   feed is exhausted" and stalling an outbox cursor permanently.

3. **The filesystem change-log append fsyncs whenever `FlushToDisk` is on, with the throughput
   measurement as a hard gate.** No second option was added, because the docs tell durability as one
   lever and the existing caveat is written as a caveat *of* `FlushToDisk`. The measurement is not
   advisory: the implementer records 200-append cost at both option values before and after, and
   **reports BLOCKED rather than proceeding if `FlushToDisk = true` append cost more than triples**,
   at which point reversing to an opt-in `FlushChangeLogToDisk` is a decision with data behind it.
   The related admission is that the fsync itself is not black-box provable — nothing in this
   repository proves `AtomicWriteAsync` fsyncs either — and the plan says so rather than shipping a
   timing assertion dressed as a mechanism proof.

4. **The unbounded in-memory and Redis feed growth stays parked, and is named the top Phase 11
   candidate.** It is a genuine defect — `MaxRevisions` and `MaxBytes` exist to bound memory and do
   not bound it on two providers — and it was left undone specifically because the coherent fix
   ("feed retention follows stream retention", making all four providers uniform) *changes the
   published feed semantics of the two providers that currently retain everything*. Today
   `docs/providers/index.md` tells operators that Redis and the in-memory provider have no prune loss;
   the fix would make that false. Trading a documented no-loss property for a documented memory bound
   is a product decision, so it is flagged here rather than taken quietly inside a close-out phase.

One thing this phase deliberately did **not** decide: nothing in Phase 10 is a new capability, so the
"Forwarding policy (decided before Phase 7, 2026-09-05)" classification list is unchanged,
`docs/architecture/capabilities.md` gains no row, and no cell flips.

## Addendum (pre-Phase-11, 2026-09-09)

Decisions taken while writing the Phase 11 section and its implementation plan. **As in Phases 8, 9
and 10, they were taken without `AskUserQuestion` because the session ran under an autonomous
`/goal`.** Seven are worth revisiting if that ruling was wrong, and each is listed with what
reversing it would cost.

1. **Feed retention follows stream retention, unconditionally.** The rule is "a record leaves the
   change feed exactly when its history record leaves the store", and it is taken as a behaviour
   change rather than hidden behind a knob. This is the decision Phase 10 explicitly deferred to the
   maintainer, and it is taken here because the alternatives are not honestly implementable: an opt-in
   `TrimChangeFeed` flag would be **silently ignored on three of five providers** — Entity Framework
   Core's feed *is* its history table and the filesystem provider's pruned history file is simply
   gone — which is what the capability honesty rule and Phase 10's "implemented exactly or not at all"
   ruling forbid; and a feed bound independent of stream retention invents a second retention
   vocabulary and admits a new loss shape, a record dropped from the feed while its history survives.
   The mitigation is real and not rhetorical: `StateRetentionPolicy.KeepAll` is the default with every
   bound null, so a default-configured store loses nothing, and the change is observable only to a
   deployment that configured a memory bound and is not getting it. The window is `0.4.0-alpha` with
   no 0.4 consumer, and Phase 10 already took a breaking change to this interface in it. **Reversal
   cost:** two statements of production code and one in-memory structure, plus re-flipping six
   documentation locations. The structure change is the part that would not simply revert, because
   the read now takes a lock it did not take before.

2. **The filesystem page-scan regression is fixed in Phase 11, not deferred again.** It is a
   regression Phase 10 introduced and documented rather than a pre-existing limitation, and the
   standing instruction for this effort is that incomplete work ships rather than waits. Keeping it
   parked would leave a documented "raise `BatchSize`" workaround standing for a cost the library
   creates. **Reversal cost:** none in code — deferring it again would simply have meant a smaller
   phase — but the documentation would keep telling operators to tune around a defect.

3. **The incremental read is an in-process memo inside `FileSystemStateLedgerStore`, not a
   cursor-carried byte offset.** `StateChangeCursor` stays a bare `long`, and no cursor store, file
   format, Redis value or Entity Framework Core column changes. The cursor form is more general and
   survives a process restart, but it breaks four `IOutboxCursorStore` implementations and one
   persisted JSON shape, pushes a store-specific field into a type documented as portable, and cannot
   help the case that motivates it — a cursor read back after a restart carries a previous process's
   view of the file. The memo also shortens the window `_changeFeedGate` is held, which the cursor
   form would not. **Reversal cost:** the memo is private to one class and can be deleted, restoring
   the previous read verbatim; the tests written for it would be deleted with it.

4. **Redis prune becomes atomic between history and feed through one `ITransaction`**, rather than two
   sequential `SortedSetRemoveAsync` calls. Prune is already a non-atomic read-then-remove against a
   concurrent append, so the transaction is not closing that window; it is stopping a reader from
   seeing a feed that still serves a record the history no longer holds. The two keys span hash slots,
   so prune becomes standalone-only — the shape `ImportAsync` and `CaptureAsync` on this provider
   already document, so no new Redis Cluster constraint is added. The removal is member-exact `ZREM`
   and never `ZREMRANGEBYSCORE`, because sorted-set scores are IEEE doubles exact only to 2^53, which
   is the Phase 6 lesson `MaxImportablePosition` already encodes. **Reversal cost:** two lines — the
   transaction becomes two awaited calls again, at the price of a visible half-pruned window.

5. **The in-memory feed becomes an `ImmutableSortedSet<FeedEntry>`, published under `_feedLock` and
   read lock-free.** Two smaller designs were rejected, one on paper and one by running it. A
   `ConcurrentDictionary` keyed by position is the smallest diff and is wrong on correctness: its
   enumeration is not a snapshot, so a reader could observe position P+1 without P and a paging
   consumer would advance its cursor past P forever — a lossless-within-retention violation
   introduced by a change meant to bound memory. A mutable `SortedSet` read under `_feedLock` was the
   plan's first design; the Task 1 implementer found that it turns the read into a wait on the
   writer's critical section, and that two existing in-memory tests which pause a writer inside that
   lock and drain meanwhile deadlock rather than fail — they pin a documented, in-memory-specific
   guarantee stronger than the shared one (a drain during an in-flight append sees a prefix,
   immediately). The immutable set keeps that guarantee for the same reason the queue had it — a
   reader works on a structure that is never mutated — and buys O(log N) insert and remove.
   `System.Collections.Immutable` ships in the shared framework on every target, so the core
   package's zero-dependency rule holds. **Reversal cost:** returning to a lock-free *mutable*
   structure means returning to a queue, which cannot be trimmed — so reversing this means reversing
   decision 1 as well; returning to the locked mutable set means rewriting the two tests to accept a
   blocking read, which is a weaker guarantee than the one they document.

6. **The scan-cost figures get a committed, env-gated measurement harness before the fix lands.** The
   2.3 / 18.5 / 83.7 ms figures in two documents have no artifact behind them, and Phase 10's fsync
   task already established that a performance claim carries a before and an after. Figures published
   in documentation are labelled as taken on the development machine rather than as a contract, and
   the harness asserts nothing on wall-clock time — a threshold on a shared CI runner is a flake, not
   a gate. **Reversal cost:** deleting one test class; the cost of not having it is that "the fix
   worked" would again be unprovable, which is the pattern this phase exists to stop repeating.

7. **Six items are parked with named homes rather than left implicit**, and the list is written with
   the phase rather than after it: the Entity Framework Core test-provider seam bundled with its SQL
   Server / PostgreSQL CI job and the cross-address append race (one deliverable, Phase 12);
   `_changes.log` compaction, which is the actual fix for filesystem feed *storage* growth that
   decision 1 does not address (Phase 12, and decision 3's memo is built to survive it);
   cross-process filesystem append locking (unchanged Phase 10 ruling); `MessageId` casing (0.4
   design); `IsolationLevel.Snapshot` (needs a server engine, so it pairs with the seam);
   and `ManualTimeProvider.CreateTimer` (orthogonal, small). **Also parked and newly documented
   rather than fixed:** re-importing an existing revision at a *different* position leaves feed
   residue on three providers — Redis keeps a changes member with no history twin, the in-memory
   provider keeps the old entry, and the filesystem provider's old log line now dereferences to the
   rewritten history file so the record yields twice. It is the colliding-lineage restore
   `docs/providers/index.md:167` already describes; Phase 11 adds a comment at each import site and
   one sentence in the providers doc. **Reversal cost of the parking, collectively:** each item is a
   later phase's work rather than a decision that has to be undone; the one that would cost something
   to have got wrong is the import residue, because documenting a defect rather than fixing it is only
   defensible while the scenario stays the unsupported one the docs say it is.

Nothing here is a new capability: the "Forwarding policy (decided before Phase 7, 2026-09-05)"
classification list is unchanged, `docs/architecture/capabilities.md` gains no row and flips no cell,
and `CapabilityMatrixTests.cs` is untouched.
